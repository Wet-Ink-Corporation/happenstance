Read 2026-10-11 · LiveStore `livestorejs/livestore@3cb74e62` and `livestore-contrib@c375b5ab` (both 2026-10-05), npm 0.4.0 (beta, Apache-2.0) · happenstance `main@6da1032`

## The answer

LiveStore sits at the opposite end of the one axis that matters most for happenstance-sync. It keeps **one total order per log**, arbitrated by a central backend that refuses any push that is not a fast-forward. Clients then **rebase** their pending events on top, which rewrites local history. Happenstance has frozen the reverse:

- ingest never refuses (SY-1);
- events append at the tail (SY-5);
- peers need not agree on an order (SY-19);
- a refused spoke keeps its log (SY-34).

So LiveStore's sync core is a **negative reference**. It is a well-built, carefully documented example of the design §5 rejects, and LiveStore's own RFC 0002 names the cost: *"Event rebasing gives us convergence without correctness."* In DCB terms, a rebase moves an event past facts its append condition never saw, so the consistency decision it was written under quietly stops holding.

The value to inherit sits around that core. The best of it is in LiveStore's **bugs and gaps**. Each one is a real wrong implementation that happenstance's sync testkit can be written to reject: a non-atomic chunked append, a server that only validates the first event of a batch, every error collapsed into "unknown", positional dedupe that materialised an event twice, and an offline test that was a no-op stub. The second source is operability: a sync-status surface, backend-incarnation detection, error classes the runner can act on, and pagination hints. The third is guidance for the typed layer and the browser.

Adopt · 11 · Adapt · 8 · Reject · 6 · Already aligned · 5 **Nothing here reopens a frozen clause.** Every adopt or adapt verdict either lands as a new conformance rule or wrong implementation in `happenstance-sync-testkit`, goes in as an additive field on a type that is still unpublished, or becomes evidence in ADR-0026 (#105) or ADR-0027 (#106). There is one exception, finding L-22, and it is flagged where it appears.

## Proposed issues

Filed on 2026-10-11 at Ryan's request as \#242 to \#247. All sit under epic \#64 (phase 13). Every one is a two-way door: the sync crates are unpublished, so even the port change in P-2 is free until the port freezes. Labels follow `.github/tracker.yml`.

### Sync testkit: ingest atomicity and durability falsifiers from LiveStore

`type:task` `area:sync` `source:audit` `status:blocked` 

What  
Three rules for `happenstance-sync-testkit`, each with a wrong implementation in the testkit's `tests/`:

- `ingest_group_is_atomic_under_a_mid_group_fault`, against an ingest that chunks one group into several unwrapped statements;
- `ingest_validates_every_event_not_the_head`, against one that checks only `events[0]`;
- `ack_never_confirms_a_non_durable_event`, against a peer that acks before commit.

Why  
LiveStore ships all three defects: D1 chunked append (`sync-storage.ts:163-195`), head-only validation (`push.ts:76-78`), and an ack-ordering decision taken only after the fact. Each is a plausible wrong implementation, so none of these rules is decorative.

Blocked by  
\#111 (the suite's macro) and \#108 (`IngestStore` made real).

Done when  
Each rule is green on `MemorySyncPeer` and red on its mutant.

### Classify peer errors so the runner can choose between retry, split, park and stop

`type:task` `area:sync` `source:audit` `status:needs-owner` 

What  
Give `SyncPeer::Error` a classification the runner can read: a bound such as `Error: Classify`, or a `fn class(&self) -> FailureClass` with `Transient`, `Split`, `Park`, `Stop` and `#[non_exhaustive]`. Add a testkit rule that drives every refusal a fixture can produce and checks its class.

Why  
Two of LiveStore's four providers report every failure as `UnknownError`, and as a result they "error out instead of reconverging". The port's `Error` is opaque today, so happenstance's runner could not tell the classes apart either. The classes line up with SY-33 (transport refusals retry; authorisation refusals stop) and VT-25 (`ExceedsStoreLimit` parks).

Decision  
It shapes the port, so it belongs in ADR-0026 (#105). That is why it is needs-owner. It is two-way until the port freezes.

### Runner: per-edge sync status, peer incarnation check, bounded backoff

`type:feature` `area:sync` `source:audit` `status:blocked` 

What  
- A `SyncStatus` value for each edge: confirmed watermark, local events above it, last failure class, a retention-gap flag (SY-32), and the far side's last-seen `StoreId`s.
- If that `StoreId` changes, the edge stops and reports. It never resets the local log (SY-34).
- The outbound buffer is bounded, and backoff is jittered and capped.

Why  
LiveStore's `syncStatus()` and `backendId` check are the parts operators use most. Its unbounded queues (#1423) and unjittered retry are the parts to avoid.

Blocked by  
ADR-0026 (#105), and \#104 for what "restored" means on Postgres and Neon.

### `Pulled` says whether more is waiting

## How far to trust the sources

- LiveStore's own specs are all marked *Draft*, and its docs and code disagree in at least five places. Who assigns the global sequence number: the docs say the backend, the code says the client. Client-id collision handling: the docs describe it, and the code has a TODO. Custom merge: the docs both claim and disclaim it. Push validation, and whether a crash divergence heals, also differ. Every claim above cites code where code exists, and docs only where they are the sole source.
- The S2 and Electric providers live in `livestore-contrib` and are outside LiveStore's conformance matrix. Only the Cloudflare provider enforces the fast-forward contract. Their defects are used here as examples of wrong implementations, not as LiveStore's intended behaviour.
- GitHub's issues API was unreachable from this session. Issue numbers (#253, \#254, \#255, \#1423, \#1416) come from links in LiveStore's docs, so their open or closed state was not checked.
- Everything on the happenstance side was read at `main@6da1032`, chiefly from `spec/SPECIFICATION.md` §5, `crates/happenstance-sync/src/` and `runbook/phases/13-sync.md`.
