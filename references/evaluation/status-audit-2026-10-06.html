Status-quo audit · 6 October 2026

Happenstance status audit

Audited snapshot 1f92d08 (same as main) Read-only: no changes were made to the repository

The foundation is real, published, and unusually well tested. What is left is the larger half of the vision: offline sync, a stable read-model layer, docs a newcomer can learn from, and the first outside user. At the pace seen so far, a credible 1.0 is about four to seven months away. A single scope decision could cut that by a third or more.

Overall: amber Solid engineering, behind its own plan, and the hardest part has not started.

Where we are on the road to 1.0

The milestones on the 1.0 path, in the order the roadmap runs them.

  1. Foundations: phases 0–12

    Done

    The storage contract, the certification test suite, four database adapters and the typed layer. First published as 0.2.0 on 10 September, with three releases since.

  2. Reconcile the records and define 1.0: phases 15–16

    Done

    Finished on or under estimate. 1.0 now has a written, checkable definition: nine libraries, sync included.

  3. Last chance for breaking changes, released as 0.4.0: phase 17

    In progress · 3 of 10 exit criteria

    Re-estimated from 5–8 days to 25–30 after it started. The biggest unknowns are still ahead: a Neon consistency fix, a runtime-handle question that may change two adapters' setup, and the release itself.

  4. Additions after the window: phase 17b

    Not started

    Non-breaking follow-ups split out of phase 17 so 0.4.0 does not wait on them.

  5. Read models become stable: phase 18

    Not started

    The read-model runner is still marked "unstable", and its agreed redesign (to async) has not been built.

  6. Sync between devices and servers: phase 13

    Not started

    The largest remaining item. About 10–15% exists: the interfaces and an in-memory peer. There is no sync engine, no certification tests and no networked peer.

  7. Retention and forgetting data: phase 14

    Not started

    The policy is decided (no deletion through the core interface in 1.x). The supporting work has not been built.

  8. Documentation that teaches: phase 20

    Marked in progress, nothing recorded

    1.0 depends on it, but the roadmap's day count leaves it out. No outside reader has tried the docs yet.

  9. 1.0.0 and a release-candidate soak: phase 21

    Not started

    Last by definition.

Off the 1.0 path: SQLite in the browser and on device (phases 19a and 19b, not started). The documentation website (phase 22) is built but has never gone live, because GitHub Pages is not switched on for the repository. Turning it on is a one-click setting for the owner.

What it can do today

Capabilities in plain terms, rated by how far they are proven.

Record events with consistency rules enforced at write time

Proven

Works in memory, on SQLite, on Postgres and on Neon. CI runs the full certification suite against live Postgres and Neon databases, and it passes.

A certification kit for storage back-ends

Proven

The standout asset. It is a published test suite that any database adapter must pass, and it is itself tested by deliberately broken adapters it has to catch.

Typed commands with automatic retry

Working

An application decides on a change and appends it. Conflicts and busy databases are retried for you. A given/when/then test helper comes with it.

Run at the edge on Cloudflare

Fails on real platform

Passes in simulation but fails a size rule on a real Durable Object, and its published limits are far above what the platform allows. A fix is written and passing, but not merged. Until then, main is red.

Read models (projections)

Unstable

They work and can be rebuilt, but sit behind an "unstable" switch. Their shape will change in phase 18, and no guide page explains them yet.

Neon (serverless Postgres)

Known gap

Published and passing, but a known read-consistency rule fails intermittently. The fix is an open phase-17 item.

Sync between devices and servers

Designed only

Interfaces, data formats and an in-memory peer exist. Nothing yet moves events between real stores.

Graph read models (Ladybug)

Retired

Finished, then retired because it could not be published. Nothing replaces it, so 1.0 has no non-SQL store.

Top risks to a credible 1.0

Ranked by how likely each is to delay 1.0 or make it disappointing.

  1. The least-built part is on the critical path

    The owner chose to include sync in 1.0, against the plan's own recommendation. It is a third or more of the remaining effort, and its rules have no tests yet.

  2. 1.0 would freeze an interface no outsider has used

    Every user of the core library today is inside this repository. Once 1.0 is out, changing the interface costs every adopter a major upgrade. Nobody outside the project has yet tested it in real use.

  3. The schedule has slipped once and is under-counted

    The one phase re-estimated mid-flight grew about five-fold. The roadmap's 1.0 figure leaves out the documentation phase and the release soak.

  4. One maintainer, with heavy process

    Work comes in bursts (12 active days in the last 29). Keeping the planning records consistent is now a sizeable job in its own right. Whether that slows delivery was not measured.

  5. Platform limits on edge and serverless

    Cloudflare's real limits sit below the specification's minimum. Neon's consistency gap is still open. Both have plans, but neither is closed.

Recommended next moves

Ordered by leverage, quick unblockers first.

  1. Get main green and the site live days

    Merge the Cloudflare limits fix (PR #35, already passing) and turn on GitHub Pages so the documentation site deploys. Refresh the handover note, which still describes merged work as open.

  2. Decide whether sync belongs in 1.0 owner decision

    This is the biggest lever on the date. Shipping 1.0 as seven libraries and giving sync its own 0.x line removes 22–40 days from the critical path. It also lets sync's design meet real use before it is frozen.

  3. Find two or three outside users now calendar time

    Their feedback is the only evidence that the interface 1.0 freezes is right, and recruiting them takes weeks of waiting rather than effort. Start before 0.4.0, not after.

  4. Timebox the remaining phase-17 unknowns and ship 0.4.0

    Put a fixed limit on the Neon consistency spike, and fall back to a documented exception if it is not solved in time. Answer the runtime-handle question inside the window. Consider a small 0.3.3 that carries only the SQLite busy-timeout fix, which has waited 15 days for 0.4.0.

  5. Write the guides a newcomer actually needs

    Read models, upgrading from 0.3 to 0.4, choosing a store, and passing the certification suite. These matter more than polishing the pages that already exist.

  6. Close the testing gaps that matter

    Run the live-Postgres read-model store (the one the read-model interface was finalised against) in CI. Back the "final" rules that have no check yet, or mark them as unchecked.

  7. Trim the process to fit one maintainer

    The records are thorough but drift within days. Fewer hand-maintained status documents, and fewer citations by line number, would cut the upkeep without losing the decision history.

How this audit was done
  • Run against an isolated copy of main at 1f92d08. The working branch was untouched, and nothing was committed or pushed.
  • The full quality gate was run for real and passed. Five of the seven examples were also run, and the other two ran as part of the gate's tests.
  • Nine independent readers mapped the vision, plans, specification, code, docs, history and process. Eight assessors then scored them. Every important finding went to two separate checkers who tried to disprove it: 27 were confirmed, 26 were confirmed only in part and reworded to match the evidence, and none were rejected outright.
  • Not verified here: the live Postgres and Neon tests and the deployed Cloudflare tests (CI results were read instead), and the optional dependency-licence and nightly doc checks (tools not installed). Git history before 7 September 2026 is not in the repository.
  • The full findings, with file-and-line citations, are in the accompanying detailed report.
