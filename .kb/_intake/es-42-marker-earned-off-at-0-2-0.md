# ES-42's provisional marker is earned off at `0.2.0`: `read`'s return carries no `Unpin` bound, and that is now frozen

Decision record: **ES-42-FREEZE**. Staged for `/redkiln:kb-ingest` rather than
written as an atom by hand, because accepted decision atoms are authored by that
command and hand-writing one produces the directory layout of the process without
the process.

**Status: decided by the repository owner at the `0.2.0` release pass.** The
specification and `RUNBOOK.md` already carry the outcome; this brief is the
reasoning, which is the half a marker change cannot hold.

---

## What forced it

ES-42's marker did not merely record uncertainty — it named a **deadline**:

> *Must be re-evaluated before phase 12: adding a bound to an opaque return type
> after publish is breaking, so this clause expires rather than drifts.*

It was, at the moment the release pass began, **the only clause in the
specification whose own marker gated publication**. Every other `[PROVISIONAL]`
and `[DEFERRED]` marker names a falsifier and an owning phase; this one named a
point in time, and that point was now.

It was also, at that moment, **missing from `RUNBOOK.md`'s falsifier ledger** —
one of five rows the ledger had drifted short of. Phase 12's exit criteria
instruct an auditor to check the provisional clauses *against that ledger rather
than against prose*. Followed literally, that instruction would not have surfaced
the one clause that said it had to be settled first. The ledger repair is what
found it; this decision is what the repair was for.

## The question, asked in the clause's own terms

Does any consumer need `dyn EventStore` where the port has acquired a method the
hand-written `Pin<Box<…>>` wrapper cannot box — a generic method, which is not
dyn-compatible, or a return whose lifetime the wrapper cannot name?

The marker is explicit that **inconvenience is not the falsifier**. The erasure
is roughly fifteen lines of downstream code (ADR-0011's E11), it compiles, and it
round-trips against `MemoryEventStore` with no unsafe code and no change to the
port. Wanting it in the library rather than in your own crate is not the same
claim as being unable to write it.

**The answer at `0.2.0` is no.** No such consumer exists, and none is known to be
coming.

## Why freezing is available at all

`Pin<Box<dyn Stream + 'a>>` is itself a `Stream` through the standard blanket
impl over `Pin<P>`, and `Pin<Box<T>>` is `Unpin` whatever `T` is. That is why
boxing suffices, why no pin projection is needed, and therefore why no unsafe
code appears in a workspace that forbids it outright.

What the rejected `+ Unpin` bound would have cost is the part worth keeping
visible: it permanently forbids a generator-backed stream — `error[E0277]: …
cannot be unpinned` on a `stream!` macro, compiled at E12 — which is the natural
implementation of the chunked-cursor shape. That shape has no implementation in
this workspace and therefore **no vote**, which is exactly the situation CF-25
exists to be careful about.

## Why CF-25 does not gate this freeze

Stated rather than assumed, because CF-25's standing qualification applies to
*every* `[FROZEN]` port clause and skipping past it silently is the failure mode
it was written against.

CF-25 forbids declaring a **port** frozen while an axis of §6.5's instrument
portfolio has no passing implementation at its far end. ES-42's `Rule:` is
**compile-level**. There is no adapter axis that could falsify a property of a
return *type*: an adapter cannot demonstrate that `read`'s return does or does
not need `+ Unpin`, because the property is discharged by a compiler and not by
a store. The evidence is a compile, and E11's erasure wrapper is it.

That is a narrower argument than "CF-25 does not apply to ES clauses", and the
narrowness is the point. It applies to this clause because this clause's rule is
not about behaviour.

## What would reopen it, and what that now costs

Unchanged, and deliberately kept in the clause body: a consumer that genuinely
needs the erasure and cannot write it. A frozen clause still has to say what a
mistake would look like.

What has changed is the price. While the clause was provisional, reopening was an
edit. It is now `[FROZEN]` on a published crate, so reopening costs a **new ADR**,
and adding the bound would be a breaking change requiring a major-version move
under `0.x` rules. That asymmetry is the whole reason the marker demanded a
decision *before* publication rather than after.
