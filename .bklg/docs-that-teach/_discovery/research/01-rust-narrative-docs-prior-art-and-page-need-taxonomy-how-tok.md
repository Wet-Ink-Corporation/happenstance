# Rust narrative-docs prior art and page-need taxonomy — how tokio, serde, diesel and axum split narrative from reference, what lands on docs.rs versus a book, and how each decides which need a page answers; Diataxis and its critics, since 'a page answering a second need has a defect' is that shape and is contested

## Findings

- **The two-surface split is the ecosystem norm, not an invention this initiative would have to justify.** Every large Rust crate examined (tokio, serde, diesel, axum) separates a *narrative site* (tokio.rs, serde.rs, diesel.rs — all mdBook-family static sites) from the *reference* that lives at docs.rs, and each explicitly points the reader from one to the other rather than letting them collide on one page. tokio's own crate-root doc says, verbatim, "Guide level documentation is found on the website" (https://docs.rs/tokio/latest/tokio/) — a one-line disclaimer whose only job is to stop docs.rs from trying to be the tutorial. serde's crate root says "See the Serde website https://serde.rs for additional documentation and usage examples" (https://docs.rs/serde/latest/serde/) and its README lists the split as a table of contents: overview, derive setup, examples, *then* "API documentation" as a distinct last line (https://github.com/serde-rs/serde/). diesel's crate root goes further and names the failure mode directly: "If this is your first time reading this documentation, we recommend you start with the getting started guide" (https://docs.rs/diesel/latest/diesel/) — i.e., the reference page itself tells a first-time reader they are in the wrong place.
- **axum is the counter-case, and it is instructive precisely because it deliberately declined the book.** axum has no narrative site at all; its docs.rs crate page carries "lots of code snippets and examples" directly, backed by a flat `examples/` directory whose own README says only "This folder contains numerous examples showing how to use axum" (https://github.com/tokio-rs/axum/blob/main/examples/README.md) — no ordering, no stated audience, no claim about which need each example answers. A contributor tried to fix this by writing an unofficial book from the examples and hit exactly the gap: "I was happy to see that there are lots of examples, but I was not sure in which order to try to read them" (https://github.com/tokio-rs/axum/issues/3268). A reviewer's suggested fix in that thread — turn a reproduced example into "how to model the data sent by form / how to create the handler / how to create the html form / how to test this" — is a how-to guide taking shape in real time out of what had been undifferentiated reference material. axum's gap is the visible cost of skipping the split this initiative's constraint presupposes.
- **None of the four crates states, anywhere, an explicit rule for which need a given page answers.** diesel's own "Guides" index sorts guides by *topic* ("Getting Started," "Schema in Depth," presumably others) rather than by *need* (tutorial vs. how-to vs. explanation) (https://diesel.rs/guides/). tokio's site sorts its tutorial by *build order* (Setup → Hello Tokio → …) which is Diataxis's tutorial shape by convention, not by declared policy. This means the brief's demand — "a named answer to which need does this page answer" — is *not* something any of these four ecosystem leaders currently write down; they enforce it by convention and by the physical separation of surfaces (book vs. docs.rs), not by a labeled decision per page. Naming the decision explicitly, as the brief requires, would be a stricter discipline than current Rust prior art, not a replication of it.
- **The Rust API Guidelines are reference-scoped and silent on narrative structure — confirming the open question already logged in the intake brief.** The community's own documentation standard, `C-CRATE-DOC` through `C-HIDDEN`, governs only what belongs in a doc comment (thorough crate docs, one example per public item, `?` not `unwrap`, an Errors/Panics/Safety section, hyperlinks, no leaked impl details) (https://rust-lang.github.io/api-guidelines/documentation.html). It has no opinion on tutorials, how-tos, or a book at all — Fuchsia's rubric, which extends the guidelines for an internal monorepo, likewise only adds unsafe-justification rules, not narrative-structure rules (https://fuchsia.dev/fuchsia-src/development/api/rust). The gap the intake brief names ("no rule about narrative structure... across twenty-eight constitution atoms") is real at the ecosystem level too, not just in this repository — there is no existing Rust standard to adopt wholesale for the narrative half of the problem.
- **Diataxis is the framework that gives "a page answering a second need has a defect" its exact shape, and it says so explicitly.** Diataxis "identifies four distinct needs, and four corresponding forms of documentation... and proposes that documentation should itself be organised around the structures of those needs" (https://diataxis.fr/). Its foundational claim is that this is a *complete* enumeration: "there is simply no other territory to cover" (https://diataxis.fr/_/downloads/en/latest/pdf/) — tutorials/how-to guides address *action*, reference/explanation address *cognition*; tutorials/explanation serve *study* (skill acquisition), how-to/reference serve *work* (skill application). Two production teams cited on the framework's own homepage report using it as literally that decision procedure: Cloudflare's docs team says "When we weren't sure where a new piece of content should fit in, we'd consult the framework" (quoted on https://diataxis.fr/).
- **Diataxis's own "quality" theory independently reproduces this initiative's central diagnosis.** The framework distinguishes *functional quality* (accuracy, completeness, consistency, precision — independently measurable) from a second, deeper axis, and states plainly: "Documentation can be accurate, complete, consistent and also useless" (https://diataxis.fr/quality/). That sentence is, almost verbatim, the intake brief's own framing ("documentation is accurate and unteachable, and nothing in the repository can tell the difference"). This is strong independent corroboration that "accurate but unteachable" is a recognized, named failure mode in documentation theory — not a problem this repository invented a name for.
- **Diataxis's sharpest critique attacks the totalizing "four and only four" claim, not the one-need-per-page discipline itself — and the critique names exactly the risk category this brief occupies.** Hillel Wayne's critique argues the four-document model was built to document *tools* (simple conceptual models) and breaks down for *languages* and dense-concept systems: "If you look at the Python docs, the tutorial section needs to also explain and reference... Language concept maps are just too dense to separate," and proposes a fifth, uncovered category — the *conceptual overview* — for exactly that density (https://www.hillelwayne.com/post/problems-with-the-4doc-model/). This is a direct hit on the shape of this initiative's subject matter: happenstance is documenting not a tool but a *contract with an unfamiliar conceptual model* (DCB, consistency boundaries) that the intake brief has explicitly scoped a reader who does *not* already know. Peter Williams's independent critique makes a structurally different objection — that the four-quadrant taxonomy is silent on *findability* ("we still need to get them to the right document... what do we put there?") and on indices/landing pages, meaning Diataxis classifies content but does not by itself solve navigation (https://newton.cx/~peter/2023/divio-documentation-system/).
- **Diataxis's own maintainer concedes the framework does not scale cleanly onto orthogonal structure, and that partial or blended application is expected, not a failure.** The framework's own "complex hierarchies" page states: "Diátaxis is not a scheme into which documentation must be placed — four boxes... this does not mean that there must be simply four divisions of documentation in the hierarchy, one for each of those categories" and "Documentation should be as complex as it needs to be" (https://diataxis.fr/complex-hierarchies/). A GitHub issue on the framework's own repo notes the irony that "the website describing the framework does NOT follow what it describes" — its own pages mix reference and explanation — with a Diataxis community member's reply conceding "each of the category feels far too vague" as a real usability complaint even from sympathizers (https://github.com/evildmp/diataxis-documentation-framework/issues/107). A third practitioner account (Emmanuel Bernard) reports using Diataxis loosely as "a lens through which to view content organization... to soft apply it... but not go religious about it," explicitly warning that rigid application "bring[s] back friction" (https://emmanuelbernard.com/blog/2024/12/19/diataxis/).
- **"One page, one need" independently recurs outside Diataxis, in older technical-communication theory, with the same rationale the brief states.** Mark Baker's *Every Page is Page One* (2011, predates Diataxis's popularization) argues a page must have a "specific and limited purpose," and diagnoses the opposite failure precisely: pages become "open-ended sinks into which every discovered defect of user knowledge... is poured, until they cease to serve any reader well" — his prescription for a page carrying leftover material is identical to the brief's "a page answering a second need has a defect": "ask what purpose those facts serve, and write a new topic to serve that purpose" (http://everypageispageone.com/2011/09/13/characteristics-of-eppo-topics-specific-limited-purpose/). This shows the discipline the brief adopts is a load-bearing idea independently discovered by at least two documentation traditions, not an artifact unique to Diataxis's four-box framing — which matters if the initiative wants the discipline without importing the contested totalizing claim.
- **Compiled-narrative tooling in Rust runs through `mdbook test`, and it is not friction-free at scale.** `mdbook test` shells out to `rustdoc --test` against a book's markdown, using the same code-block attributes as doctests (`ignore`, `no_run`, `should_panic`, `compile_fail`) (https://rust-lang.github.io/mdBook/format/mdbook.html, https://rust-lang.github.io/mdBook/cli/test.html). One practitioner report documents it breaking down on a real multi-feature workspace — `mdbook test`'s dependency search path is flat and collides when a crate is built under more than one feature set ("multiple candidates for rlib dependency") — and describes routing around it entirely with a `build.rs` that turns each markdown chapter into a `#[doc = include_str!(...)]` module so the book's examples run under plain `cargo test --doc` (https://jackson.dev/post/testing-mdbook-rust-snippets/). This is directly relevant to the proof-artefact requirement ("a gate step that fails on a page deliberately broken") — the naive tool exists and is standard, but at least one real workspace found it insufficiently robust for CI and had to build a second mechanism.

## Implications for the idea

- **The two-surface pattern (reference at docs.rs, narrative in a book, an explicit pointer between them) is not something this initiative would be inventing — it is the converged norm among the crates closest to happenstance in shape (tokio, serde, diesel all use it; async runtimes and serialization frameworks and ORMs, all "dense conceptual model" libraries, not simple tools).** The open question in the brief — "where each [chapter] lives, how the result is hosted" — has ecosystem precedent to weigh against rather than a blank page: mdBook-style site plus a one-line disclaimer on the crate root pointing outward is the default, and diesel's phrasing ("if this is your first time... start with the getting started guide") is a ready model for the pointer itself.
- **axum's gap is a cautionary data point for the "not a port freeze" / narrative-optional temptation.** A crate can ship without any narrative surface and be widely used — but the cost lands on exactly the reader this initiative cares about (a newcomer with no ordering signal), and a volunteer eventually tries to backfill a book from raw examples and immediately hits the "which need does this answer" problem this brief is trying to solve up front. This is evidence *for* doing the taxonomy work deliberately rather than deferring it to examples, in problem-space terms — it does not by itself argue for any implementation choice.
- **No existing Rust convention (API Guidelines, Fuchsia's rubric, or the four flagship crates) states a page's answered-need as a labeled, checkable decision.** If this initiative wants "a named answer to which need does this page answer" to be a real, checkable property (as the desired outcome demands), it is choosing a stricter discipline than any of its ecosystem peers currently practice — worth naming explicitly in distillation as a place where "prior art" means "convention," not "existing rule to import."
- **Diataxis gives the constraint its theoretical vocabulary and its two strongest justifications (the quality-theory framing that names "accurate but useless" as a real, distinct failure mode, and the tutorial/how-to/reference/explanation need-split itself) — but its own critics and even its own site concede the four-category split does not cleanly cover a dense, unfamiliar conceptual model like DCB, and Diataxis's own pages state explicitly that rigid, four-box structural adherence is not the goal.** Wayne's "conceptual overview" gap is the sharpest match to happenstance's situation: a reader who does not yet have the mental model (the intake brief scopes them *out*, but the DCB shift itself is still new to any reader who arrives from aggregates/streams) may need something Diataxis's four categories don't cleanly name. This is a genuine open tension for distillation to carry forward, not resolve here: adopt the *discipline* ("know which need each page serves; don't let a page silently serve two") without necessarily adopting the *four-and-only-four enumeration* as binding, since both Diataxis's own documentation and its critics treat the second as optional and the first as the actual source of quality.
- **The compiled-narrative proof-artefact requirement has a known tool (`mdbook test` / rustdoc doctest attributes) and a known failure mode of that tool at workspace scale (multi-feature-set dependency collisions).** This is squarely inside the adjacent "compiled-prose tooling" research angle, but it bears directly on this angle's page-taxonomy question too: whichever page-need categories get chosen, "narrative page" and "compiled example" are not the same unit, and the real-world report shows teams end up building a second mechanism when the book itself needs to compile against a real, multi-feature workspace — a shape happenstance's own workspace (many adapter crates, many feature flags) already has.
- **Findability/navigation (Peter Williams's critique) is a need Diataxis's four categories don't cover, and this initiative's open question "where each chapter lives" implicitly includes it.** A landing page or index is neither a tutorial, how-to, reference, nor explanation in the strict sense — worth naming as a fifth structural concern (not a fifth "need" in Diataxis's technical sense) so it doesn't get silently folded into one of the four and picked up the "second need" defect the brief itself warns against.
