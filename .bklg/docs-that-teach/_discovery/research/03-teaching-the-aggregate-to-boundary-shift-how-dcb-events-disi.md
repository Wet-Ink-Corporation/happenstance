# Teaching the aggregate-to-boundary shift — how dcb.events, Disintegrate, umadb-dcb, Marten and EventStoreDB move readers off aggregates and streams, the diagram vocabulary they use, and where readers reliably stall; the workspace currently contains zero diagrams

## Findings

- **Every source in this survey teaches the shift by first re-narrating the aggregate's own failure mode, in the reader's existing vocabulary, before introducing any new term.** dcb.events' `topics/aggregates/` article does not open with tags or Decision Models — it opens by reproducing the classic non-thread-safe read-check-write, then pessimistic locking, then optimistic locking with a version number, in three consecutive numbered code blocks the reader already recognizes, and only *then* names the two-Aggregate constraint (course capacity + student's 10-course cap) that neither locking strategy can solve alone. (https://dcb.events/topics/aggregates/) The pattern repeats verbatim on the home page: "To illustrate how DCB works, it makes sense first to explain the traditional Event Sourcing approach and its main issue" — Saga-coordinated dual-stream writes, the duplicate-event smell, *then* tags. (https://dcb.events/) EventSourcingDB's best-practices page and Marten's own docs open the same way: "aggregates... introduce rigidity... DCBs offer a more flexible alternative," stated as a contrast, never as a positive definition standing alone. (https://docs.eventsourcingdb.io/best-practices/dynamic-consistency-boundaries/, https://martendb.io/events/dcb)

- **The worked example is the same worked example almost everywhere: Sara Pellegrini's course-subscription scenario.** dcb.events' canonical example (https://dcb.events/examples/course-subscriptions/), Marten's `dcb-concepts.md` design table, and multiple third-party walkthroughs all reuse "a course cannot accept more than N students" + "a student cannot join more than 10 courses" as the running invariant, because it is the minimal case where a single Aggregate genuinely cannot hold both constraints without becoming a god object. This is convergent evidence that the field has settled on one canonical *cross-entity invariant* example rather than one canonical *diagram* — the story, not the picture, is what gets reused. (https://dcb.events/examples/course-subscriptions/, https://github.com/JasperFx/marten/blob/master/dcb-concepts.md)

- **dcb.events uses real diagrams, but only for the pattern it is retiring, not the one it is introducing.** The `topics/aggregates/` page contains three captioned illustrations — "The `Order` is the Aggregate root," "An Aggregate with the `Course` acting as Aggregate root with relations to `Student` entities," "Extracting the `Student` entity to a separate Aggregate, referenced by the Aggregate root identifier" — classic DDD box-and-line entity diagrams. (https://dcb.events/topics/aggregates/) The home page's own explanation of the DCB mechanism itself — single global stream, tag-based filtering, the query/append-condition cycle — contains no equivalent diagram in the fetched content: it is JSON-shaped pseudocode and prose lists ("one for the `course defined` Event... one for each subscription to the course..."). The concept being un-taught (Aggregates) is illustrated; the concept doing the teaching (tags, single stream) is described only in code and words. This is the single clearest "diagram vocabulary gap" found in the survey: the reference site for the pattern has not yet drawn the pattern.

- **A working diagram vocabulary for DCB does exist, but it was invented downstream, not at the source.** `jocelynenglund/cartshop`, a self-described teaching example ("Intended as a teaching example: the slices are deliberately thin so the consistency story is the visible thing"), built a swimlane event-model diagram with two edge colors carrying the entire consistency story: orange edges mark "events and gates touching a DCB view... gate edges carry a `!` to mark 'before this command can write, it must consult the view first,'" blue edges mark "ordinary projection fan-out, no consistency stake." The read instructions are explicit: "Read the diagram top-down per column: Actor row... Interaction row... Cart Events swimlane... Inventory Events swimlane... Spec Lane... Feedback row." (https://github.com/jocelynenglund/cartshop) This is evidence that a *legible* DCB diagram vocabulary is achievable — actor/command/event swimlanes plus a color-coded edge for "this write must check this view first" — but it had to be built by a third party writing a teaching artifact, not shipped by any of the libraries or the spec site.

- **Marten's design docs use a third diagram-adjacent form: comparison tables mapping old vocabulary to new.** `dcb-concepts.md` maps `DCB Spec Concept → Marten Implementation` (Sequence Position → `seq_id`, Tags → `tags TEXT[]` column, Append Condition `failIfEventsMatch` → `SELECT EXISTS(...)` check) row by row. (https://github.com/JasperFx/marten/blob/master/dcb-concepts.md) `martendb.io/events/dcb` narrates the mechanism as a four-step numbered list before any code: "1. Tag events... 2. Query events across streams by those tags... 3. Aggregate tagged events into a view... 4. Enforce consistency at save time." (https://martendb.io/events/dcb) This is a recurring non-diagram teaching device across the corpus — the ordered numbered list standing in for a sequence diagram — used by dcb.events itself for the DCB write cycle, by Marten for the same cycle, and by the `ingebrigtsen.blog` Chronicle writeup for its constraint/scope model.

- **Both the library authors and third-party writers name overlapping, specific misconceptions, not vague "it's hard."** In the dcb.events maintainer interview: "One common misunderstanding is that DCB means 'no modeling' or 'chaos.' People hear 'dynamic' and think we are just throwing events into a pile without structure... Another misconception is that you have to strictly choose between DCB and Aggregates." (https://docs.eventsourcingdb.io/blog/2025/12/15/kill-aggregate-an-interview-on-dynamic-consistency-boundaries/) In an unrelated LinkedIn thread, a practitioner independently names a *different* specific confusion: "DCB still confuses me in parts. In some discussions it's about vertical slicing and avoiding entity centric models; in others, it's more about how to route cross-domain events into decoupled, state-safe processing units and a way to deliver them to the core logic (ie tags). Both sound valid, but the term feels a bit overloaded." (https://www.linkedin.com/posts/antonstoeckl_dcb-eventsourcing-activity-7335556459193102336-aYpN) A third, separate thread stalls on naming itself — practitioners proposing "Enduring Object," "Group," "Slice," "Perspective" as replacements for what an Aggregate used to name, because "DCB... does not strictly differentiate its parts. The internal boundaries may overlap and change every moment... that's what makes it harder to find a catchy name." (https://www.linkedin.com/posts/richardbouska_axoniq-axonframework-eventsourcing-activity-7450460070074830848-0jYR) Three independent stall points, named by three independent people, none of them "the spec is unclear": (1) mistaking dynamism for lack of structure, (2) not knowing whether DCB is a modeling technique or a routing technique, (3) having no settled noun for what replaces the Aggregate.

- **The Rust-ecosystem libraries in this workspace's own peer set (Disintegrate, umadb-dcb) teach almost entirely through rustdoc and README prose, with zero diagrams found, and lean on a different anchor: citing the specific book chapter their approach implements.** Disintegrate's README does not diagram the shift; it cites Gregory Young's *Versioning in an Event Sourced System*, "especially in the chapter titled 'Stream Boundaries Are Wrong,'" and states plainly: "What Disintegrate provides is an implementation of the 'Cheating' chapter of Young's book." (https://disintegrate-es.github.io/disintegrate/, https://github.com/disintegrate-es/disintegrate) This is a citation-as-explanation move — pointing at existing literature instead of building new pedagogy — available to any Rust crate maintainer, orthogonal to whether a diagram exists. umadb-dcb's docs.rs page and `umadb.io` client docs skip the conceptual argument for the shift entirely and start from the wire types (`DcbQuery`, `DcbAppendCondition`) with one runnable example that reads, decides, and appends — the "why" is deferred to a one-line "created by Bastian Waidelich, Sara Pellegrini, and Paul Grimshaw" attribution and an external link, not restated. (https://docs.rs/umadb-dcb/latest/umadb_dcb/, https://umadb.io/clients/rust.html)

- **EventStoreDB, the market incumbent, teaches streams with zero contrast to DCB or aggregates at all — its docs simply assume the stream-per-entity model as ground truth, which is itself a data point about what "moving readers off aggregates" has to overcome.** "These events are logically organized into streams, typically only one stream per entity." (https://github.com/kurrent-io/ESDB-Docs-v5/blob/main/docs/streams.md) Getting-started guides across all client languages open with `appendToStream("orders", eventData)` with no discussion of why a stream boundary was chosen or what it costs. (https://docs.kurrent.io/clients/java/legacy/v5.4/getting-started, https://developers.eventstore.com/clients/grpc/reading-events.html) A reader arriving from EventStoreDB-shaped docs — the most widely deployed event store — has had the stream-per-entity model presented as the default, unmarked case, never as one option among several; that is the starting mental model any DCB-adjacent library's docs must actively dislodge, not merely supplement.

## Implications for the idea

- **The workspace's own aggregate-to-boundary story (DCB-native from the start, never had aggregates to kill) is the opposite shape of every source surveyed, and that changes what "teach the shift" even means here.** Every example above teaches by first re-narrating the reader's *existing* pain (their aggregates, their sagas, their duplicate events) and then relieving it. happenstance's audience — a reader who has installed the crate — has no aggregates to feel pain about yet; a page that opens the way dcb.events opens ("here is the traditional Aggregate problem you already have") would be teaching a problem the reader doesn't have, to justify a solution they haven't asked for. This is squarely a problem-space finding, not a solution: it means the content decision of *which prior mental model to anchor against* (DDD Aggregate reader? Stream-per-entity/EventStoreDB reader? No prior event-sourcing exposure at all — explicitly out of scope per this initiative's non-goals) is unresolved and worth naming as an open question for distillation, since the survey shows every other project picked a specific anchor rather than writing in a vacuum.

- **The diagram-vocabulary gap found at dcb.events — the retiring concept is drawn, the arriving concept is not — is a warning, not a template.** If the initiative's docs draw nothing (current state: zero diagrams in the workspace, per the seed), that matches the least-taught path found anywhere in this survey. If it draws only the old model (boxes/roots) for contrast without ever diagramming the tag/query/append-condition cycle itself, it reproduces dcb.events' own gap exactly. The one project that closed this gap (cartshop) did so with a swimlane + colored-edge convention built specifically as a teaching artifact, external to the reference implementation. This is evidence, in the problem space, that *a diagram convention for the write-side consistency cycle itself* (not just for entity relationships) is the missing artifact class in the ecosystem generally, not only in this workspace — which raises without answering it, since choosing a convention is solutioning, the question of whether this initiative's proof artefacts (the friction log, the deliberately-broken gate page) should specifically probe whether a non-author reader gets through the query/append-condition cycle without a picture.

- **The three independently-named stall points (dynamism mistaken for chaos; modeling-technique vs. routing-technique ambiguity; no settled replacement noun) are testable friction hypotheses, not documentation content to copy.** Because happenstance's own vocabulary already diverges from the field's most common terms — this workspace uses `Tags`, `AppendCondition`, `SequencePosition` per the DCB spec directly rather than Marten's `IEventBoundary`/`FetchForWritingByTags` or Disintegrate's `Decision`/`StateQuery` — the friction-log reader (the proof artefact this initiative already commits to) is a direct probe for whether happenstance's chosen nouns land or reproduce the third stall point (no name sticks). This is an argument for what the friction log should watch for, not for renaming anything.

- **The convergent "same worked example everywhere" finding (course capacity + 10-course cap) is evidence that a single well-chosen cross-entity invariant carries more teaching weight across this field than any diagram, table, or code sample style — and the workspace already has one.** `examples/course-subscriptions/` is named identically to the pattern the entire ecosystem converged on independently. This is a signal (not a recommendation) that the example the workspace already runs is doing real pedagogical work by genre convention, which is worth surfacing to whoever answers "what the chapters are" in distillation, since it means the initiative is not choosing a worked example from nothing — it is deciding whether to lean into, rename, or diverge from an example the rest of the field already treats as canonical.

- **EventStoreDB's total silence on aggregates/DCB as a contrast (stream-per-entity presented as unmarked default) means a reader arriving from the most common event-sourcing background will not have "aggregates are the old model" primed at all — they'll have "one stream per entity" primed instead.** happenstance has neither aggregates nor per-entity streams; its docs will need to decide whether they are arguing against a reader's *stream* intuition, a reader's *aggregate* intuition, both, or neither — this is a scoping question for distillation, not one this research can settle, but the survey shows it is the load-bearing decision every other project in this space made explicitly and early.
