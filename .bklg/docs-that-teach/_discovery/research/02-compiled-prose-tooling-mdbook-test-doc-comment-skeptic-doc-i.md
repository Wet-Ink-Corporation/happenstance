# Compiled-prose tooling — mdbook test, doc-comment, skeptic, #![doc = include_str!], trybuild; which of these can fail a CI gate on a deliberately broken page rather than merely compiling a good one

## Findings

- **`mdbook test` fails a build by default on broken Rust code, with no configuration required.** It runs `rustdoc --test` against every fenced Rust code block in every chapter; a block that fails to compile, panics at run time, or (if marked) fails to panic when it should, produces a non-zero process exit and a `FAILED` line naming the chapter and the line number. `rust-random/book`'s own issue tracker shows exactly this shape of failure in the wild: six code blocks failed to compile after an API rename, and the CI run reported each one by chapter name and line (`update-0.8.md - Updating_to_0_8::Distributions (line 124)` etc.). This is a page catching its own drift, not a designed-in demo. — https://github.com/rust-random/book/issues/79
- **The mdbook maintainers' own CI recipe treats a green `mdbook test` as the gate**, not an optional nicety: their GitHub Actions example and the `rust-lang/book` workflow both run `mdbook test` on every push and PR with no special-casing. `rust-lang/book`'s current workflow (which pins mdBook 0.5.1 and toolchain 1.97 — the same MSRV as this workspace) goes further: it builds an external crate (`trpl`) first and passes its `deps` directory via `--library-path` so that code blocks exercising a real dependency graph, not just `std`, are checked. That is the shape a Rust narrative book needs when its examples call a real crate rather than toy code. — https://github.com/rust-lang/mdBook/wiki/Automated-Deployment:-GitHub-Actions, https://github.com/rust-lang/book/blob/main/.github/workflows/main.yml, https://rust-lang.github.io/mdBook/continuous-integration.html
- **`mdbook test`'s blind spot is a page whose author opted out, not a page that lies while compiling.** The `ignore` attribute on a code fence tells both `rustdoc` and `mdbook test` to skip a block entirely — syntax-highlighted, never compiled, never run. The seed's own diagnosis calls a book of ` ```ignore ` fences "the documentation form of a `todo!()` body: it type-checks against anything," and that is literally true here: `ignore` opts a block *out* of the type checker rather than through it. A gate built on `mdbook test` alone cannot distinguish "no narrative pages use `ignore`" from "narrative pages use `ignore` everywhere" unless something separately audits fence attributes. Unspecified-language blocks (` ``` ` with no `rust`) are tested as Rust by default and are a documented source of false failures for command-line transcripts — the maintainers' own workaround discussion (issue #179) shows this is a known false-positive mode, not a hazard to teaching correctness. — https://github.com/rust-lang/mdBook/blob/master/guide/src/format/mdbook.md, https://github.com/rust-lang/mdBook/issues/179
- **`mdbook test` needs `rustdoc` on `PATH` and a pre-built dependency tree, and silently degrades to a hard, opaque failure when either is missing** — not a "skipped" state. A live GitLab CI thread from 2025 shows the exact failure: `mdbook test` errored with `No such file or directory (os error 2)` because the CI image had no Rust toolchain at all, and the fix was installing `rustdoc` explicitly. This is a "the gate step ran and errored for the wrong reason" risk this workspace's `xtask` already has a doctrine for (the phase-2 "generated 3 warnings, exited 0" rustdoc incident below is the same category — a step that *looks* wired but isn't). — https://github.com/rust-lang/mdBook/issues/2544
- **`doc = include_str!` and its predecessor `doc-comment` both make a README's code blocks first-class doctests, subject to the same compile/run/panic checks as any doc comment** — no separate tool, no build script. Since Rust 1.54 the stdlib mechanism is `#[cfg_attr(doctest, doc = include_str!("../README.md"))]` on a dummy item (or the rustdoc book's own recommended form, `#[doc = include_str!("../README.md")] #[cfg(doctest)] pub struct ReadmeDoctests;`); a broken code fence inside that README fails `cargo test --doc` exactly as a broken example in `lib.rs` would. `doc-comment` (the crate) is the pre-1.54 workaround for the same effect via a `doctest!("../README.md")` macro, and its own docs say the crate is now largely unnecessary — "unless you need to support older Rust versions, you don't need this crate." Its last release was 2022 dated by docs.rs listings scraped, and its README explicitly nominates the stdlib mechanism as the modern replacement. — https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html, https://docs.rs/doc-comment/latest/doc_comment/, https://crates.io/crates/doc-comment
- **The one sharp edge of `doc = include_str!` for a README is diagnostic quality, not detection.** A Stack Overflow thread from a maintainer confirms: a failing block inside an included README is *found* — `cargo test` fails, non-zero exit, gate stops — but it is reported as `test src/lib.rs - sequence (line 22) ... FAILED`, with the file name of the *including* item, not the README, and a line number relative to the assembled doc comment rather than the source markdown. The failure is real; the pointer to fix it is degraded. This workspace already compiles all four READMEs as doctests per `CLAUDE.md`, so this edge is already live, not hypothetical, for any narrative page reusing the same mechanism. — https://stackoverflow.com/questions/69117817/how-can-i-tell-cargo-to-run-code-test-in-documentation-in-my-readme-md
- **`skeptic` gets Markdown code blocks to a real compiled test *without* being rustdoc, but the project is effectively dormant and its own README recommends the lighter tool instead.** Its most recent crates.io release is 0.13.7 dated 2022-02-01, and its README's final section reads: "If you don't need advanced features but just to test markdown content, the doc-comment crate might better match your needs." Skeptic's genuine differentiator — the reason a well-known Rust book toolchain (rust-lang/rust-cookbook) chose it historically — is that it compiles each fenced block as a *standalone* `.rs` file with its own `main`, rather than wrapping it the way rustdoc does, and it requires `countryblock` be explicitly tagged ` ```rust ` (GitHub's own convention) rather than assuming untagged fences are Rust the way rustdoc/mdbook does. That is a real, still-valid distinction for a book with many non-Rust fences, but it comes at the cost of a build-script + `OUT_DIR` + generated-file plumbing this workspace's own doctrine (skeleton crates, pinned tool paths in `xtask/`) would need to own explicitly, against a crate whose maintenance signal is weak. — https://github.com/budziq/rust-skeptic, https://crates.io/crates/skeptic
- **`trybuild` fails a gate on deliberately broken code by design — but it is not a narrative-prose tool, and its blind spot is the opposite of the others': it verifies *diagnostic text*, not *documentation correctness*.** A `trybuild::TestCases::compile_fail(...)` test is only satisfied when the named source file fails to compile **and** the compiler's stderr matches a checked-in `.stderr` snapshot byte-for-byte (or is regenerated with `TRYBUILD=overwrite`, which the maintainer's own docs flag for manual `git diff` review). `trybuild`'s own README is explicit that this is for testing *error message quality* — e.g., a proc-macro's diagnostics — and explicitly discourages using it to exhaustively call public APIs with wrong argument types "there would be no benefit." It has no concept of a Markdown page, a chapter, or narrative prose at all; every test case is a standalone `.rs` file the harness compiles directly. It is the right tool for "does this crate's compiler-error UX stay good," which is a different claim than "does this teaching page still match the API." — https://docs.rs/trybuild/latest/trybuild/, https://github.com/dtolnay/trybuild/
- **rustdoc's own `compile_fail` doctest attribute is the narrative-page-native version of what trybuild does for library code, and it is strictly weaker.** `compile_fail` on a fenced block makes a doctest pass only if the block *fails* to compile — a genuinely deliberately-broken block can be asserted as a permanent, checked teaching artifact (e.g., "here is the mistake the API is designed to prevent, and the gate proves it stays prevented"). But on stable Rust it checks *only* that compilation failed, not what error was produced; the optional `compile_fail,E0044`-style error-code assertion exists on nightly only, and even the rustdoc team's own unstable-features page says it is "unlikely to be stabilized" because specific error codes for a given mistake are not considered a stability guarantee across compiler versions. A community forum thread on this exact question confirms the same limit from the user side: "there's no good way to specify which error it should result in." A `compile_fail` block can therefore drift silently from "fails for the reason the page claims" to "fails for some unrelated reason" without the gate noticing — the block still goes green either way. — https://doc.rust-lang.org/rustdoc/write-documentation/documentation-tests.html, https://doc.rust-lang.org/rustdoc/unstable-features.html, https://users.rust-lang.org/t/checking-which-compile-time-errors-happen/86859
- **This workspace's own phase-2 incident — "rustdoc does not read `RUSTFLAGS`, so the documentation step printed 'generated 3 warnings' and exited 0" — is a *documented, currently-open upstream issue*, not a workspace-specific bug that was fixed by switching tools.** `cargo test --doc` (which drives every doctest, README-included or not) genuinely does not honor `RUSTFLAGS` for the doctest-compilation step, and as of an April 2024 cargo issue, `RUSTDOCFLAGS` is *also* silently dropped by `cargo test --doc` specifically (as opposed to `cargo doc`, which does read it) — the maintainers closed it as a duplicate of a five-year-old upstream rustc issue (#67533) that remains open. This means: any gate step that relies on `-D warnings` or `--cap-lints` reaching doctest compilation to catch a *silently-degraded* teaching example (one that compiles but should be denied for style/lint reasons) needs a mechanism other than the environment-variable convention this workspace already uses for the rest of its lints — the failure mode that bit this repository once is structural, upstream, and still live today. — https://github.com/rust-lang/cargo/issues/13697, https://github.com/rust-lang/cargo/issues/4737, https://github.com/rust-lang/cargo/issues/6650, https://doc.rust-lang.org/cargo/reference/environment-variables.html
- **None of these five tools, alone, closes the full space of "a page can be wrong without the gate noticing."** Each is precise about a *different* class of brokenness: `mdbook test`/`doc = include_str!` catch "the code no longer compiles or panics" but not "the code compiles and runs but no longer demonstrates the claim the prose makes around it" (this is exactly the seed's own worked example — three handlers that "compile, run, and are the same append-condition shape by accident," a hazard nothing in this list would have caught, because the code is correct, it just isn't teaching what the prose says it teaches). `compile_fail`/`trybuild` catch "this should not compile" but are blind to *which* error fired once past stable's floor. `ignore`-tagged fences opt out of every one of them. A CI gate proving "narrative pages are compiled against the real crates" is therefore a claim about *code correctness inside prose*, and is a strictly narrower claim than "a reader can be taught" — worth stating precisely so the proof artefact this initiative commits to (a gate step that fails on a deliberately broken page) is scoped to what compiled-prose tooling can actually detect, not stretched to imply it detects pedagogical drift too.

## Implications for the idea

- **The proof artefact this initiative already commits to — "a gate step that fails on a page deliberately broken to prove it" — is achievable with stock, well-known tooling; none of these five require inventing anything.** `mdbook test` and `#[doc = include_str!]` both fail loudly, by default, on a code block that no longer compiles, and both are exercised in production by rust-lang's own book. This is reassuring evidence that the constraint "narrative documentation is compiled by the gate or it does not ship" is not aspirational — it is the default behavior of the ecosystem's own book tool, not a bespoke integration this project would be first to build.
- **The gate's claim needs to be scoped honestly, because "compiles" and "teaches correctly" are different properties and this research shows exactly where they diverge.** A page whose code still compiles but silently drifted from what the surrounding prose asserts (the seed's own `Tags::empty()` example, or the append-condition-shape hazard in `course-subscriptions`) will pass every tool surveyed here. Naming that boundary explicitly — "this gate proves a page's code still matches the real API surface; it does not prove the page still teaches the right lesson with that code" — keeps the proof artefact from over-claiming, and points toward the friction-log / non-author-reader artefact (already named in the intake brief) as the *only* instrument in scope that catches pedagogical drift, not code drift.
- **`ignore`-tagged fences are a live audit target, not a hypothetical one.** Because both `mdbook test` and standard rustdoc treat ` ```ignore ` as "skip, don't compile," a documentation standard adopted from this research needs an explicit position on when (if ever) `ignore` is permitted on a narrative page — otherwise the gate can be green while a page silently reverted to prose-only. This is exactly the failure the seed already caught once in the testkit's own doctests ("elaborate spellings of `ignore`"), and the same failure mode is available to any future narrative page unless something greps for it.
- **The `RUSTFLAGS`/`RUSTDOCFLAGS` gap is not closed by picking any tool on this list — it needs a separate decision.** Every one of these tools ultimately routes through `rustdoc`'s doctest machinery (directly, or via `cargo test --doc`), so the "gate step ran green but didn't actually enforce the lint level it claimed to" incident this workspace already suffered once is a property of the *mechanism*, not of which crate wraps it. Whatever documentation standard results from this initiative should record that fact rather than assume switching from bare rustdoc to `mdbook test` (or vice versa) fixes it — it doesn't; the report already exists that `cargo test --doc` drops `RUSTDOCFLAGS` too.
- **A README-included doctest's degraded failure message (wrong file name, wrong line number) is a real authoring cost worth naming, not a defect to route around with a heavier tool.** Since this workspace already compiles all four READMEs as doctests, any narrative page reusing the same `#[doc = include_str!]` pattern inherits the same "found the bug, mislocated the pointer" property. That is a fact about how a broken page gets diagnosed by a maintainer, which matters to whichever page-need this work eventually assigns to "how a caught regression gets fixed," even though it is out of scope to solve here.
- **`skeptic`'s effective dormancy (last release 2022, its own README pointing elsewhere) and `trybuild`'s narrow, non-narrative scope (diagnostic-text testing, not page testing) both argue for narrowing rather than widening the tool surface a documentation standard needs to describe.** The stronger the case for "the ecosystem's own two mechanisms — `mdbook test` for a book, `#[doc = include_str!]` for anything published as a crate doctest — already cover the compiled-prose claim," the less this initiative needs to justify a third dependency, which matters given the brief's own constraint that any new tree the gate reads must be pinned by path in `xtask/src/` the way `spec/` and `standards/rust/` already are.
