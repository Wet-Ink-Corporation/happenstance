## Questions

- **Does the rule need a `Fixture` seam, or can it be written without one?** **Answered as far as discover can answer it, and the shape is fixed either way.** The rule needs the store to lose something *during* the rule, and nothing on `Fixture` can ask for that today (`_decomposition.md:277-279`). If the instrument's own `Fixture` can express forgetting through a seam it declares, the addition is a **defaulted** `Capability` const plus a **defaulted** method that panics naming both ways of reaching it, gated in the rule by `require!(F: …)` so a declining fixture reports `RuleOutcome::Skipped` and the test is still emitted — never `#[cfg]`-ed out, which `crates/happenstance-testkit/src/contract.rs:31-42` rejects by name. **A required item is not available**: it breaks every existing `Fixture` impl in and out of the workspace and is an AC-011 violation, not a trade-off. Whether the seam is needed at all is settled at `spec` against the instrument as built; the answer "no seam" is preferred and is the one to try first.
- **Capability or fact?** **Answered:** a `Capability`. `crates/happenstance-testkit/src/contract.rs:44-54` draws the line — a capability is a **trade** (the fixture could have co-operated and owes a reason), a limit is a **fact**. *"Can you be made to forget?"* is a trade, because any store could co-operate in a test. What a store *does not hold* is a fact and has **no home on `Fixture` at all**: that is ES-39's port primitive, and putting it on the fixture would be answering ES-39 in a place no application can read (`_decomposition.md:299-305`).
- **DT-7 — one signal or three?** **Deferred to HS-S0120.** It does not reach this rule: `positions_are_not_reused_after_removal` asserts a property of *positions*, not of any signal the store emits about its own completeness. The rule is written so that it stays true under either DT-7 answer, which is also what keeps it inside the no-surface-change constraint.
- **Is "fails loudly" expressible in the existing error vocabulary?** **Answered, and for this story the answer is yes — but only because this rule does not need it.** The loudness here is the conformance suite's own: a named rule going red against a named mutant, which is the mechanism `RUNBOOK.md:4667` asks for ("a rule name rather than 'conformance failed'"). No `EventStore` error variant, no third condition outcome and no new return type is required. The general answer — that a *reader* cannot be told loudly without a surface the port lacks — is HS-S0118's and HS-S0119's finding and HS-S0124's escalation; it is recorded here only to note that **this** story does not collide with the constraint.
- **Does the mutant fail *exactly* this rule?** **Deferred to `spec`, against the code.** A store restored from a truncated snapshot may also disturb `contains_event_id` or head monotonicity. `mutants_fail_exactly_their_declared_rules` (`crates/happenstance-testkit/tests/mutation_coverage.rs:2889`) checks both directions, so the spec must either narrow the mutant to a single defect — the one-defect-per-store discipline `mutants.rs` documents — or declare the full `fails` list honestly. Declaring more rules is allowed; a mutant that fails a rule it did not declare is not.

## Decision

ES-38 is `[FROZEN]` and names a rule that has never been written, for a reason the clause itself records: writing it needs a store events can be removed from, and no such store existed — the obligation was assigned to phase 14 by name (`spec/SPECIFICATION.md:4309-4319`), and HS-S0114 has now removed the blocker. This story writes `positions_are_not_reused_after_removal` into `crates/happenstance-testkit/src/suite.rs`, registers it exactly once in `for_each_event_store_rule!`, and lands the wrong implementation the clause itself names — an adapter that renumbers on compaction — as a registered `REGISTRY` row rather than as prose. The spec will cover: the rule's assertion, written against positions the store actually assigned rather than against literals; that it is green against `MemoryFixture`, against the honest instrument in both retained configurations, and against every other registered fixture; the `Defect` implementing DA-2(a)'s rebuild-through-`MemoryEventStore::restore` construction and its `REGISTRY` row with a non-empty `fails` list; both meta-tests green in both directions; and — only if the rule genuinely cannot be written without it — a `Fixture` seam in the exact defaulted shape `MID_BATCH_FAULT` set, with `require!` gating so a declining fixture reports a stated reason instead of vanishing from the binary.

## The wrong implementation

**`CompactingRestoreStore` — a store that, on removal, rebuilds itself from the events it kept.** This is the mutant, it is named by ES-38's own `Rejects:` line (`spec/SPECIFICATION.md:4321-4323`), and it is not hypothetical: it is exactly what `MemoryEventStore::restore(store_id, retained)` produces, because `append` assigns `position_at(first_index + offset)` where `first_index = stored.len()` (`crates/happenstance-core/src/memory.rs:386-389`, `position_at` at `:277-282`). A store rebuilt from a three-event suffix therefore begins issuing `1, 2, 3` again — positions it has already assigned and already acknowledged to a writer. **It passes every check in the workspace today**, because the rule that would catch it does not exist: `positions_are_not_reused_after_removal` is absent from `for_each_event_store_rule!` (`crates/happenstance-testkit/src/registry.rs:94`). It is also the obvious move for a device pruning to save space, and it silently invalidates every checkpoint and every replicated `after` naming that store. **Its home is `crates/happenstance-testkit/tests/mutation_coverage/mutants.rs`, with a `Declared` row in `REGISTRY` at `crates/happenstance-testkit/tests/mutation_coverage.rs:324` whose `fails` list names this rule** — a row with an empty `fails` list is rejected by `mutant_registry_is_exhaustive` (`:2754`, and the reason at `:318-320`).

Two ways this story could go wrong while everything stays green, both worth writing into the spec as things the rule must survive:

- **The rule that reads its own instrument's floor.** A rule written against a suffix store, comparing against that store's *first retained position*, is asserting a value the retained predicate chose. It passes, it looks like it checks renumbering, and it would pass just as happily against a store that renumbered from a different base. The assertion must be against positions the store actually assigned before and after removal — captured from `append`'s own return, never written down.
- **The mutant that fails for the wrong reason.** A `Defect` that rebuilds *and* loses its `EventId` mapping fails several rules, one of which is this one, and `mutants_fail_exactly_their_declared_rules` (`:2889`) is what catches the sloppiness. The discipline `mutants.rs` documents — one defect per store, so a red rule is red for the declared reason — is what makes a red build informative rather than merely red.

And the standing one, because this story is where the temptation lands: **the instrument is an instrument first and a target never** (`project.md:141-145`). If a `Fixture` seam is added for this rule, it is defaulted and declined by every other fixture; the suffix store itself stays in `crates/happenstance-testkit/tests/` and gains no export.

**The two ticks that needed judgement.** *Literal position values*: this is the story where the box bites hardest, because the rule is **about** positions and the specification permits gaps (VT-11), so an assertion on `[1, 2, 3]` would convert a `MAY` into a `MUST` with no ADR behind it. Two concrete bans follow and are carried into the spec: the rule captures the positions `append` actually returned, before and after removal, and asserts non-reuse and strict monotonicity **between those captured values**; and it never names the instrument's first retained position, which is arbitrary — chosen by the retained predicate and different in the suffix and scattered configurations. A rule that hard-coded it would be green against this instrument and meaningless against any other. *`[FROZEN]` clauses*: ES-38 is `[FROZEN]` and this story touches it, but **changes nothing in it**. It writes the rule ES-38 already names, discharging an obligation ADR-0013 created and ES-38 records (`spec/SPECIFICATION.md:4318-4319`); the clause's normative text — no position reuse, unique and strictly monotonic, `Query::all()` means every event the store holds — is implemented, not amended. The one edit anywhere near ES-38's text is removing the `(new)` annotation from its `Rule:` line once the rule exists, and that belongs to HS-S0123, which raises it rather than assuming it.
