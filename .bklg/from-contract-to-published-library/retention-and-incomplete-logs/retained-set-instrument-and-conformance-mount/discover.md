## Questions

- **DT-7 — one undifferentiated incompleteness signal, or transient / benign-permanent / meaningful-permanent?** **Deferred to HS-S0120** (`dt-7-signal-shape-and-the-redaction-answer`), which owns AC-009. It is deliberately not answered here, and this story is built so that either answer remains reachable: the retained predicate is a *test-side* parameter, not a signal the store reports, so the instrument does not prejudge how many kinds of hole exist. What this story does owe DT-7 is evidence, and the pass list (HS-S0115) is it.
- **Is "fails loudly" expressible in the existing error vocabulary?** **Answered here, and the answer is no** — this is the question flagged as most likely to collide with the constraint (`_intake-brief.md:64-67`), and it is answered before the instrument is built rather than after a reader has been written against a signal that does not exist. Three checks against the code: `Guard::is_violated_by` is a two-arm `match` with no third outcome (`crates/happenstance-core/src/append.rs:249-252`); `read_decision_model` returns `(Vec<SequencedEvent>, Option<SequencePosition>)` with no completeness channel (`crates/happenstance-core/src/store.rs:321-331`); `contains_event_id` returns `Result<bool, _>`, in which `false` means both *"never had it"* and *"minted it and forgot it"* (`crates/happenstance-core/src/store.rs:268`, and DA-8 at `_decomposition.md:381-397`). So a *typed* loud failure needs a surface this port does not have. **What is expressible inside the constraint** is loud failure as an **observed recorded value** — the actual wrong fold, the actual `false`, the actual stall — which is exactly the tier `RUNBOOK.md:4658-4668` asks for. This story's job is to make those observations possible; naming the missing surface is DA-7's option table and HS-S0124's escalation.
- **Does the instrument need a `Fixture` seam at all?** **Deferred to HS-S0116.** DA-4 (`_decomposition.md:276-308`) says the shape if one is needed — a **defaulted** `Capability` const plus a **defaulted** panicking method, mirroring `MID_BATCH_FAULT` (`crates/happenstance-testkit/src/contract.rs:207-211`, `:297-307`) — and says to add **nothing** if the rules can be written without it. This story adds nothing; the rule that might need it is ES-38's, so its author decides.
- **How generic must the decorator be?** **Answered: not very, and that is recorded.** CF-27 says *"a decorator over any `EventStore`"*; a fully generic decorator over `S: EventStore` buys nothing this project needs. If genericity is dropped, it is recorded in ADR-0028 as a deliberate narrowing of CF-27's text so the clause and the instrument agree (`_decomposition.md:551-555`).
- **Where does the instrument live, exactly?** **Answered:** a new target under `crates/happenstance-testkit/tests/`, beside `fixture_instruments.rs`, never `src/fixtures/` (AC-A01, `_decomposition.md:502-505`).

## Decision

Every store in this workspace holds its whole log, so the completeness axis has nothing at either end and a contract that quietly assumed completeness has never been contradicted — a holed log and a young log are the same value at every seam the port exposes (`spec/SPECIFICATION.md:4260-4272`). This story builds the missing far end as an *instrument*: a decorator over a live inner `MemoryEventStore`, parameterised by a retained predicate over positions so it can present both a suffix and a scattered hole, that forgets by hiding at the port rather than by rebuilding its inner store — positions therefore stay unique and strictly monotonic across the hole, which is what keeps it the honest store rather than ES-38's mutant. The spec will cover: the retained-predicate parameterisation and its two required configurations; the `Fixture` impl presenting an **empty** store at `connect()` exactly as `MemoryFixture` does, so no failure it later produces is a seeding artefact; the filtering `read` written as a `Stream` adapter with `ReadOptions` applied over the retained set rather than under it; `head` reporting the highest retained position and `contains_event_id` answering `false` for a forgotten event that this store minted; the `event_store_conformance!` mount in a new `crates/happenstance-testkit/tests/` target; and the rustdoc that states in the type's own words that it is an instrument and never a target, together with the CF-25/CF-26 limitation that hiding discharges falsifiability and not implementability.

## The wrong implementation

**The mutant this story rejects: `RestoringSuffixStore` — an instrument built the obvious way, by rebuilding its inner store from a filtered snapshot.** It is one line of `MemoryEventStore::restore(store_id, retained)` away, it is the shape `DurableFixture::reopen` already uses at `crates/happenstance-testkit/tests/fixture_instruments.rs:190-193`, and it looks like the instrument this story is asked for: it presents a store holding only part of its log, it compiles, and it passes most of the suite. It is wrong because `MemoryEventStore::append` assigns `position_at(first_index + offset)` where `first_index = stored.len()` (`crates/happenstance-core/src/memory.rs:386-389`, `position_at` at `:277-282`) — so a store restored from a three-event suffix begins assigning `1, 2, 3` again and **reuses positions it has already assigned**, which is ES-38's `Rejects:` verbatim: *"an adapter that renumbers on compaction"* (`spec/SPECIFICATION.md:4321-4323`). Nothing in the workspace catches it today, because `positions_are_not_reused_after_removal` is absent from `for_each_event_store_rule!` (`crates/happenstance-testkit/src/registry.rs:94`) — which is the whole reason this project exists. **Its home is `crates/happenstance-testkit/tests/mutation_coverage/mutants.rs` with a `REGISTRY` row at `crates/happenstance-testkit/tests/mutation_coverage.rs:324`**, and it is registered there by HS-S0116, which writes the rule that fails it. This story's obligation is the negative one: build the *other* construction, and hand HS-S0116 the rejected one as a free, faithful mutant rather than shipping it as the instrument.

Two sharper mutants this story must also not become, both of which pass every existing check:

- **A reader-facing decorator that never exercises the hole.** A suffix store that is only ever read from its own first retained position never reads across the gap, so it returns a complete-looking fold and the entire experiment is vacuous. The defence is DA-1's scattered configuration plus `from` naming a position rather than an index — the semantics `read_from_a_gap_position` already documents at `crates/happenstance-testkit/src/suite.rs:1523-1531`, where the failure mode is stated as *"a projection resuming across a gap then stalls forever with no error anywhere"*.
- **The instrument that quietly becomes a target.** A decorator over any `EventStore` that passes most of the suite reads as a working store, and one `pub use` from `src/fixtures/` publishes it (`project.md:337-339`). AC-013 is checked by location, by absence from the three publishable crates' public API, and by rustdoc that says so — it is an **instrument first and a target never**.
