## Questions

- **Is "fails loudly" expressible in the existing error vocabulary?** **Answered, and for this reader the answer is the strongest no in the project.** A projection runner resumes from a checkpoint, which is a `SequencePosition` and nothing else; `EventStore::read` with `from` set to that position returns the events above it and has no channel to say that history below or between was destroyed (`crates/happenstance-core/src/store.rs:119`). The suite's own text predicts the consequence — the runner *"stalls forever with no error anywhere"* (`crates/happenstance-testkit/src/suite.rs:1529-1531`) — and a stall is the exact opposite of loud. Making it loud requires one of DA-7's four options, every one of which is a port surface and a `0.3.0` this initiative's exit criteria do not contemplate. **So this story's honest outcome is expected to be a negative result**, recorded under AC-006's second sentence with the missing surface named, and escalated by HS-S0124 rather than fixed here. It is answered now, at discover, rather than after a runner has been written against a signal that does not exist — which is what `_intake-brief.md:64-67` asked for.
- **DT-7 — one signal or three?** **Deferred to HS-S0120.** The evidence this story owes it is specific: does the runner's observable state differ at all between a benign suffix prune and a scattered regulated purge? If it stalls identically under both, that is a concrete argument that the three-way distinction cannot be *delivered* to this reader without a new primitive, which is DT-7's cost side stated as a measurement rather than an opinion.
- **What happens if the runner does not exist when this story starts?** **Answered: halt and report.** HS-P0011 is rank 1 and this project is rank 5, so the runner is expected; if it is absent, that is a dependency failure to raise, never a licence to write a bespoke one — *"a hazard demonstrated against a reader nobody ships proves nothing"* (`_storymap.md:73`; `_decomposition.md:130-134`). The story's spec must state the halt condition and what it reports, so the blocker is legible rather than discovered as a stalled implementation.
- **Does this story settle `read_from_a_gap_position`'s ownership?** **Explicitly no, and this is the story where it must be said out loud.** The rule exists and is registered (`crates/happenstance-testkit/src/suite.rs:1490`); the open question is who owns it, and it is the *sibling* half of the atom this project resolves. It is deliberately not adopted (`project.md:124-127`), and HS-S0121's narrowed successor atom is what keeps it open. This story may **cite** the rule's documented hazard as prior art — that is what it is for — and may not extend, re-home or close it.
- **What exactly is recorded?** **Deferred to `spec`, with the shape fixed:** the checkpoint the runner resumed from, the events it actually received, the checkpoint it held afterwards, whether it advanced, and whether anything anywhere produced an error or a log line. A stall is evidenced by the absence of progress plus the absence of an error, so both absences must be captured deliberately rather than inferred from a test that simply did not fail.

## Decision

A projection runner is the reader with the least equipment to notice a hole: it resumes from a checkpoint that is a bare `SequencePosition`, reads forward, and has no channel through which a store could tell it that history it never saw is gone. The suite already writes the consequence down — a projection resuming across a gap stalls forever with no error anywhere — but nothing has ever been able to stage it, because every store in the workspace holds its whole log. This story runs the real runner, the one `happenstance` provides over core's checkpoint pump per ADR-0007, against HS-S0114's instrument in both retained configurations, and records its actual state. The spec will cover: the halt condition and its report, if HS-P0011's runner has not landed; the observation harness and where it lives; the checkpoint the runner resumes from, derived from positions the store actually assigned rather than written down; the captured after-state — events received, checkpoint held, progress made or not, errors emitted or not — under both a suffix and a scattered hole; the comparison between the two configurations as evidence for DT-7; and the written finding that this reader cannot be told loudly without a port primitive it does not have, recorded against AC-011 with DA-7's option named, and no change made.

## The wrong implementation

**`SilentlyResumingRunner` — a projection runner that resumes across the hole, reads what is above its checkpoint, advances, and materialises a read model built from a log missing the events that define it.** It satisfies every existing check, and it is not a hypothetical mutant: it is what any correct-looking runner does today, because there is nothing for it to check. The read model it produces is internally consistent, its checkpoint is monotonic, its transaction discipline is intact — and it is wrong, in the way E2E-47 is wrong: a claim materialised in four seconds from three engineer notes with no registration, no policy, no reserve and no closure (`spec/SPECIFICATION.md:4364-4367`). Its sibling failure, the one the suite predicts, is `StallingRunner`: a runner whose `from` is treated as an index or an equality seek somewhere below it comes back empty across the gap and then *"stalls forever with no error anywhere"* (`crates/happenstance-testkit/src/suite.rs:1529-1531`) — no panic, no error variant, no log line, and a dashboard that is merely stale. **Both belong in this story's observation harness under `crates/happenstance-testkit/tests/`, captured as the actual materialised state and the actual stalled checkpoint**, per `mutation_coverage.rs`'s discipline against tests that record only that something failed.

Three more that would leave this story green and hollow:

- **A bespoke runner written because HS-P0011's had not landed.** It would demonstrate the hazard perfectly and prove nothing, because no application ships it — and it would quietly convert a dependency failure into a finished story. The correct move is to halt and report (`_decomposition.md:130-134`).
- **A runner resumed only from the instrument's first retained position.** It never crosses the hole, materialises a complete-looking model, and the observation is vacuous — the sharpest way to satisfy this story's letter while exercising nothing. The scattered configuration exists precisely so that survivors sit below the hole, which a suffix-only resume can never reach.
- **A "loud failure" that is a log line.** `warn!("gap detected")` inside the harness reads as loudness in a report and is invisible to the caller, who still receives a stream of events and a checkpoint and can branch on neither. Loudness the caller cannot act on is not loudness; the honest result here is the negative one, recorded.

Standing constraint: **the instrument is an instrument first and a target never** (`project.md:141-145`). Nothing in this story exports it, promotes it out of `crates/happenstance-testkit/tests/`, or adds a convenience seam to `happenstance` to make the runner easier to point at it.
