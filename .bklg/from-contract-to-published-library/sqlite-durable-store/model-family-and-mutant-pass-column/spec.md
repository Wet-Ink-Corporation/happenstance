## One-line PR slice

Take `event_store_model_conformance!` green against the durable `SqliteFixture` and put `SqliteEventStore` in the mutant harness's pass column — discharging AC-006 from the adapter's own test target per architecture brief §10, and making the racing rules' falsifier read in this adapter's own spelling (`BEGIN DEFERRED` probe-then-insert) on the row that already carries it.

## Executive summary

`sqlite-fixture-and-whole-suite` made `event_store_conformance!` green against a real file, and `concurrency-family-and-contender-count` made the racing family green with ADR-0022's runtime seam in place. Two of the four macros `project.md` DoD 2 owes are therefore green. **This PR lands the third**: the model family, which is the only thing in the suite that ever runs `read` against a store whose contents it did not choose (`crates/happenstance-testkit/src/model.rs:14-17`), and which generates the `query × from × backwards × limit × condition × position policy` space no hand-written rule set covers (`model.rs:4-12`). Against a store whose SQL was written to satisfy named examples, that is the first instrument capable of finding a *generated* disagreement, and it is where a wide-query merge or a page boundary that is right on every example goes wrong.

The delta on the mutant harness is smaller than the story map's one-liner implies, and the correction is the second half of this PR rather than a footnote. The story map says to add "the `BEGIN DEFERRED` probe-then-insert row to `mutation_coverage/mutants.rs`'s `REGISTRY`". **That row cannot exist.** `mutant_registry_is_exhaustive` rejects a row whose `fails` list is empty, a probe-then-insert store fails *no* sequential rule — that is the entire point of it — and the testkit's own README states the consequence in as many words: a concurrency rule's wrong store goes in `racers.rs` and `RACERS` (`crates/happenstance-testkit/README.md:106-113`; `crates/happenstance-testkit/tests/mutation_coverage.rs:3389-3395`). The store the story map asks for **already exists**: `RacingProbeStore` (`crates/happenstance-testkit/tests/mutation_coverage/racers.rs:352-366`), declared against `exactly_one_of_n_contenders_commits` and `k_disjoint_boundaries_admit_exactly_k_commits`, and named by `spec/SPECIFICATION.md:3728-3729` as "the store that passes every sequential rule and fails this one".

So what this PR actually owes on that half is: re-run the harness and record the verdict; amend `RacingProbeStore`'s `RACERS` provenance so it names `BEGIN DEFERRED` — the SQLite spelling ADR-0022 settles — rather than only the driver-convenience-API spelling it carries today; and write the "no `REGISTRY` row is possible here" finding down where the next reader meets it, so it is not re-opened as a gap in six months. Adding nothing and saying nothing would leave AC-007's third split (`_storymap.md` Coverage table: *"the registry row that proves the rejection is live"*) discharged by silence.

## Context pack

Read this section and you can start. Everything below the anchors table is retrieval, not prerequisite.

**1. The model family is one rule, and it is macro-emitted rather than registry-keyed.** `for_each_model_rule!` names exactly one rule, `ops_agree_with_the_model` (`crates/happenstance-testkit/src/model.rs:712-722`, rule body at `:598`). It carries its own enumeration beside its rules rather than in `suite.rs`, which CF-22 permits explicitly — "three families with one list each is the arrangement, not the exception" (`spec/SPECIFICATION.md:7775-7823`). **Do not add the model rule to `for_each_event_store_rule!`**, and do not write a model rule into `suite.rs`: `cargo xtask spec-trace` scans `suite.rs` for `pub async fn`, so a rule written there needs a clause claiming it by name and this family is one macro, not N rules.

**2. The model is not agreeing with itself, and that is a property somebody paid for.** It is built on `Query::matches` and `AppendCondition::is_violated_by`, each pinned to an independently-written naive definition by a property test in `crates/happenstance-testkit/tests/properties.rs` (`model.rs:19-38`). If a generated case goes red, the burden is on the adapter, not on the model — *unless* the failure is about position density, in which case read point 3 first.

**3. The generator emits `Anchor`s, never literal positions — and `AUTOINCREMENT` makes that load-bearing here.** A generated `ReadOptions::from(5)` is meaningless against a store that assigns positions in steps of seven from 4096, and that store exists (`GappedPositionStore`). Resolution happens once per operation and the resolved value goes to both the model and the store (`model.rs:44-61`). This adapter's positions come from `AUTOINCREMENT` and therefore **may gap after a delete** (`project.md` risks; `CLAUDE.md`, *never assert on literal position values*). If the model family reports a disagreement that turns out to be a density assumption, CF-6 says that is a finding about the *rule*, not the store — but the first hypothesis for a red model run against this adapter is the adapter's SQL, because the model has been driven against a gapped conformant variant for a phase already and agreed with it (`MODEL_COVERAGE`, `crates/happenstance-testkit/tests/mutation_coverage.rs:2333`).

**4. The feature gate cannot be expressed the way the reference harness expresses it, and this is the first thing to get wrong.** `event_store_model_conformance!` exists only behind the testkit's off-by-default `proptest` feature and only off `wasm32` (`model.rs:81-88`; `crates/happenstance-testkit/Cargo.toml` `[features]`). `crates/happenstance-testkit/tests/memory_model_conformance.rs:27` gates itself with `#![cfg(all(not(target_arch = "wasm32"), feature = "proptest"))]` — but that works **only because it is inside the testkit**: `cfg(feature = …)` names the *current* crate's features, so `happenstance-sqlite` cannot cfg on a dependency's feature at all. **Decision for this story:** enable it at the dev-dependency site — `happenstance-testkit = { workspace = true, features = ["proptest"] }` in `crates/happenstance-sqlite/Cargo.toml`'s `[dev-dependencies]` — and gate the invocation on `not(target_arch = "wasm32")` only. The alternative that lost: mirroring a `proptest` feature on `happenstance-sqlite` that forwards to the testkit. It loses because the testing brief names `cargo test -p happenstance-sqlite` as this project's conformance command (`_decomposition.md` testing brief §2, §6), and a family that needs an extra flag to appear is a family that silently does not run — the exact failure this project exists to retire.

**5. Only the tokio emitter can drive this store, and that has to be stated rather than discovered.** The reference harness invokes *both* shipped emitters as CF-23's demonstration that the emitter is still a parameter (`memory_model_conformance.rs:21-25, 31-37`). `__emit_model_blocking` runs the rule under the testkit's own `block_on` with no tokio runtime anywhere (`model.rs:748-766`), and this adapter's read stream resolves its `spawn_blocking` runtime with `tokio::runtime::Handle::try_current`, turning a runtime-less poll into `SqliteEventStoreError::NoRuntime` rather than a panic (`crates/happenstance-sqlite/src/event_store.rs:20-32`). A blocking-emitter invocation would therefore fail on the *read* path for a reason that is not a conformance defect. This story invokes `__emit_model_tokio` (the default arm) and records the declension of the blocking emitter with its reason, in the harness's own module doc — not by omitting it silently. CF-23 is satisfied for this family by the testkit's own harness; it is not this adapter's obligation to demonstrate a second emitter, and pretending otherwise would convert a runtime fact into a red rule.

**6. AC-006's "pass column" is discharged from the adapter's own target, and the refusal is reasoned.** The pass-column meta-test is `mutation_coverage::conformant_variants_pass_everything` (`xtask/src/proof.rs:90`), and its stores are `Rc`/`RefCell` primitives built inside the *testkit's own* test binary. Registering `SqliteEventStore` there would make the published testkit dev-depend on an adapter that dev-depends on it, and would drag `rusqlite` plus a tokio runtime into a harness deliberately built to need neither (`_decomposition.md` architecture brief §10). **Recommended reading, adopted here:** every registered rule driven against a conformant `SqliteFixture` *is* what that meta-test asserts, and that is exactly what `event_store_conformance!(SqliteFixture::new())` plus this story's model invocation do. The verdict, and the reason testkit-side registration was refused, is written into the story's `_ledger.md` and into the harness module doc — because "we decided not to" that nobody can find reads identically to "nobody looked".

**7. The `REGISTRY`-row instruction in the story map is structurally impossible, and the honest landing place already holds the store.** `mutant_registry_is_exhaustive` rejects an empty `fails` list; a probe-then-insert store fails no named rule; `RACERS` is the concurrency family's registry and `RacingProbeStore` is already in it, pinned to both racing rules with `expect` strings naming the *too many winners* side (`mutation_coverage.rs:2534-2555`). ES-25 `[FROZEN]` names it by name (`spec/SPECIFICATION.md:3726-3729`). What is genuinely missing is that its provenance says "no `BEGIN` between them … what an adapter writes when its driver's convenience API is one statement per call" and never says `BEGIN DEFERRED`, which is the spelling architecture brief §6 identifies as *this* adapter's form of the defect. Amending that string is a real deliverable: `every_mutant_states_its_provenance` (`mutation_coverage.rs:3059`) checks a provenance exists, and review checks it is the right one.

**8. No watchdog, no timeout, no retry loop around any rule.** CF-33 forbids a rule reading a clock (`crates/happenstance-testkit/src/concurrency.rs:24-43`); a hang under the model family is evidence about ADR-0022's busy-timeout paragraph, not something `#[timeout]` may paper over (testing brief §4). The proptest case budget is a *generator* parameter, not a watchdog, and the distinction matters when the model family runs hundreds of op sequences against a real file.

**9. The persona-journey slice.** The user here is the adapter author and the library's consumer, and the only observable increment either gets is the same one — *a store that has passed the bar* (`_storymap.md`, preamble). This story's increment is specific: the bar this adapter clears stops being a list of examples somebody wrote down and becomes a generated space, and the harness that certifies the bar is itself re-run and shown to still discriminate. BR-03 says nothing counts toward an outcome until it has passed the suite (`project.md`, *How this advances the initiative*); ADR-0010 says a rule may not be trusted to pass until a store exists that fails it (`.kb/decisions/0010-the-suite-must-prove-itself.md`, *Decision*). This story is where both sentences are applied to the same adapter in the same PR.

`crates/happenstance-sqlite/src/**` is in the boundary deliberately and is the one entry a reviewer should challenge. The model family exists to find generated disagreements that named examples miss; when it finds one, the fix is in this adapter's SQL, and narrowing the boundary to `tests/**` would force the honest fix into a different PR or, worse, into a weakened invocation. It is **not** licence to re-open decisions the earlier slice took — a change to `append`'s transaction shape, to the schema, or to the read stream's ceiling is a finding against `append-atomicity-and-store-limits`, `schema-migration-and-identity` or `lazy-read-with-snapshot-ceiling` and is escalated, not absorbed.

## Data and migrations

**N/A — no schema change, no migration, no persisted-data shape decided here.** Migration 1 and the `StoreId`/`recorded_at` columns are `schema-migration-and-identity`'s (`_storymap.md`, `durable-event-store` slice), and this story runs *against* that schema rather than altering it. Adding, renaming or indexing a column to make a generated op sequence pass would be re-deciding a settled story from inside this one, and is a finding to escalate.

Three data-adjacent facts an implementer needs anyway, none of which is a migration:

- **The fixture's file is real and per-instance.** The model family drives hundreds of generated op sequences; each proptest case runs against a fixture instance whose backing store must be fresh, and each instance owns its own temp file with `Drop` cleanup (architecture brief §11 — a process-local ordinal, no new workspace dependency, `tempfile` is deliberately not in `[workspace.dependencies]`). `SqliteEventStore::open_in_memory` remains the wrong constructor: a private in-memory database is per-connection, so a second `connect()` would open a second, empty database.
- **Positions may gap and nothing may assume `+1`.** `AUTOINCREMENT` is load-bearing precisely so positions are never reused after a delete; the model's symbolic `Anchor` is the mechanism that keeps a generated read meaningful against that.
- **Nothing is written outside the temp file.** No fixture in this story may point two instances at one directory, and no state may leak between proptest cases — the isolation rule (`AC-002` at project grain) already passes against this fixture and must keep passing at the higher case volume the model family imposes.

## Implementation notes (non-prescriptive)

These are orientation, not instructions; the compiler and a red run are better placed than this document to decide most of them.

- **Order that shortens the loop.** Land the manifest feature edge and the bare invocation first and let it run red or long before touching any SQL — the first thing worth knowing is whether the family even reaches `read`, since that is where the `NoRuntime` seam and the wide-query merge both live.
- **The two halves are independent and can be reviewed separately.** The model half touches `crates/happenstance-sqlite/**`; the falsifier half touches two files under `crates/happenstance-testkit/tests/`. Nothing couples them except this story's ledger, so a red model run should not hold the provenance amendment hostage.
- **Where a generated disagreement most plausibly lands**, given what the earlier slice built: the k-way merge's de-duplication on position under `backwards`, the interaction of `ReadOptions::limit` with the page budget across a chunk boundary, and `resume_from`'s inclusivity at a page edge. Those are the three places named examples are thinnest and the generator is densest.
- **Reading the outcome word matters.** The model family is not capability-gated, so a `Skipped` here means a `require!` nobody accounted for — treat it as a finding, not as a pass.
- **The provenance amendment is prose, not structure.** Add the `BEGIN DEFERRED` sentence to `RacingProbeStore`'s doc comment and to its `RACERS` provenance string; leave `fails` and both `expect` strings alone. `every_mutant_states_its_provenance` only checks a provenance exists — a reviewer is what checks it is the right one, which is why the sentence should name the transaction verb explicitly.
- **Write the three declensions once each, where they are met.** Module doc for the emitter, `RACERS` row comment for the registry impossibility, ledger for both plus the pass-column verdict. A decision that only exists in a ledger is one a code reader will re-open.
- **If a `.kb/_intake/` note is staged**, it records the story-map correction for the runbook's KB queue and nothing else. Never author an ADR or a `.kb/decisions/` atom as a side effect of this change.

## Clarifications resolved during spec

1. **The story map's `REGISTRY`-row instruction is wrong, and the spec corrects it rather than executing it.** `mutant_registry_is_exhaustive` rejects a row with an empty `fails` list, and a probe-then-insert store fails no sequential rule by construction. The falsifier the map wanted already exists as `RacingProbeStore` in `RACERS`. The correction became a deliverable (AC-007) rather than a footnote, because discharging `_storymap.md`'s "the registry row that proves the rejection is live" by silence is indistinguishable from not looking.
2. **The feature gate could not be copied from the reference harness.** `cfg(feature = …)` names the *current* crate's features, so `happenstance-sqlite` cannot gate on the testkit's `proptest`. Resolved to enabling it at the `[dev-dependencies]` site with `not(target_arch = "wasm32")` on the invocation. The rejected alternative — mirroring a `proptest` feature on `happenstance-sqlite` — loses because testing brief §2 and §6 name `cargo test -p happenstance-sqlite` as this project's conformance command, and a family needing an extra flag is a family that silently does not run.
3. **Only one emitter is invoked, and CF-23 is not thereby weakened.** The reference harness invokes both to demonstrate the emitter is still a parameter; that demonstration is the testkit's, discharged inside the testkit. Here the blocking arm would fail on the *read* path with `NoRuntime` — a runtime fact, not a conformance defect — so it is declined in writing (AC-003) rather than invoked and expected to be red.
4. **AC-006's "pass column" is discharged from the adapter's own target.** Architecture brief §10's recommended reading is adopted, with both refusal reasons recorded. This is a reading of `RUNBOOK.md:4221-4222`, not an amendment of it; a reviewer who requires testkit-side registration makes architecture brief §3(a) mandatory, which is a re-plan.
5. **`crates/happenstance-sqlite/src/**` stays in the PR boundary.** Debated, because a "make a family green" story reads as test-only. Kept in, because the model family's entire value is finding a generated disagreement whose honest fix is in the SQL; narrowing the boundary would push that fix into a different PR or into a weakened invocation. Guarded by naming the three settled stories a change would be re-opening.
6. **AC count unchanged from the first pass.** The seven ids the front half decided (AC-001 – AC-007) are enumerated above with nothing added or dropped, and `_ledger.md` carries exactly those seven rows.
7. **No surface, and therefore no composition ACs.** `_design.md` records "N/A — no user-facing surface" in every section including `## Sign-off`, so the COMPOSITION family in *Interaction quality* is `N/A` by the approved design; the STATE family is carried by AC-001 – AC-007 as tabulated. Writing a composition AC here would contradict what a human signed off.
8. **No ADR is authored by this story.** The story-map correction and the two recorded verdicts may be staged as a `.kb/_intake/` note for the runbook's KB queue; an atom under `.kb/decisions/` written as a side effect of a code change is out of bounds (`CLAUDE.md`, the two-places rule; `_storymap.md` on ADR-0022's authorship route).
