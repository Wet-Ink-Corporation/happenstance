## One-line PR slice

Run `cargo xtask reserve` so `happenstance-postgres` and `happenstance-neon` are
held on crates.io before a line of this project's work lands.

## Executive summary

**Pointer.** `cargo xtask reserve` already exists, is already wired into the
dispatch (`xtask/src/main.rs:670`), and already knows both of this project's
names with phase 10 recorded against each (`xtask/src/reserve.rs:98-109`). It
generates a *standalone* `0.0.0` placeholder under `target/reserve/<name>/`
carrying both licence texts, a README that says plainly it has no functionality,
and a `lib.rs` with a single `STATUS` const — then prints the dry-run and publish
commands and stops. It never publishes anything itself
(`xtask/src/reserve.rs:137-191`).

**Delta this PR lands.** The command is *run*, for both names, and the two names
become held. Concretely: two placeholder crates generated by the tool rather than
by hand, each verified with `cargo publish --dry-run` before anything is
uploaded; two irreversible `cargo publish` acts; the registry metadata for both
verified through the crates.io API rather than assumed — the same six facts phase
0 checked for the first three names (`RUNBOOK.md:1076-1083`); and the claim
written down in the two places later work reads it: phase 10's work-item checkbox
and its session log.

**What it deliberately does not land.** No workspace crate is published, no
workspace manifest changes, `publish = false` stays on both crates
(`crates/happenstance-postgres/Cargo.toml:12`,
`crates/happenstance-neon/Cargo.toml:12`), and `PUBLISHABLE` stays at three
(`xtask/src/package.rs:86`). That reconciliation is
`deskeleton-and-package-readiness`'s, and it is the story that *consumes* this
one — it cannot honestly remove `publish = false` from a name nobody holds
(`_storymap.md:76-79`).

## Context pack

The decisions this story must honour, stated as decisions. Read this section and
you can start; everything deeper is a signposted anchor below.

**1. The name is claimed when its phase starts — not earlier, and not later.**
crates.io's policy prohibits a crate that exists only to reserve a name "without
having any genuine functionality, purpose, or significant development activity on
the corresponding repository". Phase 0 claimed the three names that had code and
deliberately deferred the other seven to the phases that build them
(`RUNBOOK.md:826-829`). Both of this project's crates exist in-tree as skeletons
under active work, which is the justification the policy asks for — and *this* is
the phase that supplies it. Claiming earlier would have traded a policy violation
for nothing: crates.io has no prefix reservation, so owning `happenstance`
protects neither of these names, and the exposure is identical whenever they are
claimed (`RUNBOOK.md:815-820`). The corollary that bites here is the other
direction: claiming *later* than now means the rest of this project's ~11 days of
work proceeds against ground nobody holds.

**2. Publish the standalone placeholder, never the real crate.** This is the
decision most likely to be "simplified" by an implementer who sees two workspace
crates sitting right there. Both alternatives were considered and both lose
(`xtask/src/reserve.rs:12-30`). Publishing the real crates at `0.0.0` does not
work: `happenstance-testkit` depends on `happenstance-core` at the workspace
version, so dropping one crate to `0.0.0` cascades into every manifest naming it,
and a registry publish resolves those requirements against crates.io rather than
against the path. Publishing the real crates at their actual version is worse —
it makes the API semver-binding, and the entire plan is built around freezing the
contract *deliberately*, against evidence. **Reserving a name is not a reason to
freeze an API.** So the placeholder shares nothing with this workspace but its
metadata.

**3. The generator is the procedure; do not hand-roll the placeholder.** The
command exists precisely because the claims are weeks apart and a procedure run
that rarely from memory drifts (`xtask/src/reserve.rs:3-10`,
`RUNBOOK.md:831-837`). The specific drift it was built to prevent has already
happened once: defect D11 shipped licence *metadata* with no licence *text*,
because Cargo packages only what is inside the crate directory. That is why the
generator **copies** `LICENSE-MIT` and `LICENSE-APACHE` into the placeholder
rather than linking them (`xtask/src/reserve.rs:158-165`), and why the fix is
recorded alongside the first three claims (`RUNBOOK.md:1076-1078`). A version can
be yanked, never removed — a placeholder published without its licence text is a
permanent first impression.

**4. The tool stops at the water's edge; the publish is a human act.** `reserve`
writes files and prints two commands: the `--dry-run`, which packages and
compiles but uploads nothing, and the real publish, flagged in the tool's own
output as irreversible (`xtask/src/reserve.rs:174-188`). Run them in that order.
The token lives in `$CARGO_HOME/credentials.toml`, put there by `cargo login`;
`.gitignore:33-34` already covers the repository-local path, and nothing about
this story may put credential material into the tree, a commit message, or a
ledger entry.

**5. `0.0.0` is a name claim and nothing else.** It is not a `cargo-semver-checks`
baseline — `0.0.x` versions are mutually incompatible in Cargo, so the placeholder
buys nothing there, and the baseline is fixed separately by
`publication-and-positioning` (`RUNBOOK.md:822-824`). Do not let the reservation
be read as a release: `publication-and-positioning` (HS-P0016) owns the actual
`cargo publish` of functional versions, the `0.2.0` release, the semver diff and
the clause-ledger audit (`project.md:152-155`;
`postgres-and-neon-stores/_decomposition.md:773-788`). This project's deployment
surface is **readiness, not release**.

**6. A registry fact that is not written down in-tree is a fact this repository
cannot read.** Phase 0 did not stop at publishing: it recorded the date, the
three names, and six verified metadata facts — description, repository,
`MIT OR Apache-2.0`, README present, `rust-version`, not yanked
(`RUNBOOK.md:1076-1083`). Two later readers depend on the same record existing
for these two names: `deskeleton-and-package-readiness`, which asserts AC-012's
other half, and HS-P0016's publication audit, which is explicitly meant to *read*
what this project discharged rather than re-derive it (`project.md:276-278`).
Verification is part of the deliverable, not a courtesy — "I ran publish and it
did not error" is not the same claim as "the registry page says what we intended".

**7. One question this story must answer rather than default.** The generated
manifest hardcodes `edition = "2021"` and `rust-version = "1.85"`
(`xtask/src/reserve.rs:220-221`), while the workspace is on MSRV 1.97.1
(`Cargo.toml:8`, `.kb/decisions/0029-msrv-raised-to-1-97-1.md`, amending
`.kb/decisions/0004-edition-and-msrv.md`). Publishing as generated is defensible
— a floor claim on a crate with no code is trivially true, and it keeps these two
placeholders identical to the three already on the registry. Changing the
generator first is also defensible. What is *not* available is doing either
silently: `CLAUDE.md`'s standing instruction is **weigh the floor, do not obey
it**, and what stays forbidden is moving it, or leaving it, without saying so.
Whichever way it goes, it is recorded in this story's ledger and the published
manifest matches the decision. This is a recorded choice, not an ADR — nothing
about a `0.0.0` placeholder binds a consumer, and ADR authorship belongs to the
runbook's queue, not to a side effect of a name claim.

**The persona slice.** The "user" of this project is an adapter author and a
consuming application (`_storymap.md:19-23`), and this story is the one point
where that user is the *future* one: the stranger of initiative DoD 9 who types
`cargo add happenstance-postgres` and gets this project's crate rather than
somebody else's, and the maintainer at phase 12 who must not discover at the
publish step that a name is gone. Neither of them meets a screen, a signature or
a conformance rule here. What they meet is a registry page that says what it is,
admits it has no functionality, and points at the specification and the runbook —
which is what makes this a reservation with a stated purpose rather than the
parked name crates.io's policy prohibits (`xtask/src/reserve.rs:27-30`,
`:242-269`).

## Data and migrations

**N/A for schema.** This story creates no table, no column and no migration. The
Postgres schema — migration 1 with the phase-4 identity and time columns, tag
storage, and whatever column ADR-0024's mechanism adds — belongs to
`postgres-schema-and-live-fixture` (`_storymap.md:60`,
`crates/happenstance-postgres/src/event_store.rs:9-20`).

**But there is persistent state, and it is the reason several criteria here are
hard rather than ceremonial.** The state lives outside the repository, in the
crates.io registry, and it is **append-only and irreversible**: a published
version can be yanked but never removed, and a name, once taken, is taken. There
is no rollback and no migration path — which is precisely why the dry run, the
generated-not-hand-rolled placeholder, and the post-publish API verification are
acceptance criteria rather than notes. The in-tree half of that state is the
phase-10 session log entry at the mount point, which is what makes the off-tree
fact readable by the two later stories that depend on it.

## Implementation notes (non-prescriptive)

Nothing here is binding; the acceptance criteria are.

**A sane order.** Read Context pack §7 and settle the floor question *before*
generating, because the answer decides whether `xtask/src/reserve.rs` is in the
diff at all. Then, per name: generate, `cargo package --list` (AC-002 is cheap
and answers before any upload), dry run, publish, verify through the API. Taking
both names to the end of the dry run before publishing either is also reasonable
and costs nothing.

**On the floor question.** Both answers are defensible and the spec deliberately
does not pick. Parity with the three placeholders already on the registry is a
real argument — five identical `0.0.0` rows read better than three of one shape
and two of another — and a `rust-version` floor on a crate with no code is
trivially true. Changing the generator first is also real: the manifest is the
one thing on the page that could be read as a claim about the project, and the
project's floor moved for a recorded reason
(`.kb/decisions/0029-msrv-raised-to-1-97-1.md`). What is not available is
noticing neither. If the generator does change, remember that it changes the
*next* five claims too, which is an argument for doing it deliberately rather
than in passing.

**On the session-log entry.** Phase 0's entry (`RUNBOOK.md:1076-1083`) is the
model to copy, including its shape: what was done, the six facts as verified
values, and what was still open at the time. Write the values the API returned,
not the values `xtask/src/reserve.rs` intended to send — the whole point of
AC-006 is that those are two different questions.

**What the implementer will be tempted to do, and should not.** The two
workspace crates are sitting right there with the right names and real
manifests, and publishing them looks like less work than generating a
placeholder. Context pack §2 is the answer, and it is upstream of the type
checker — nothing in the compiler will stop it.

**No ADR is owed.** The floor decision is a recorded choice in a ledger, not a
decision record: nothing about a `0.0.0` placeholder binds a downstream
consumer, and ADR authorship belongs to the runbook's own pass rather than to a
side effect of a name claim.
