# conformance-testkit-as-a-shipped-product

## Findings

- **The pattern is old, cross-domain, and always exists for the same reason: an abstraction is claimed by more implementers than the spec-owner controls, so a private definition of "correct" stops being enough.** Java's Technology Compatibility Kit (TCK) is one of three mandatory artifacts for any JSR, alongside the spec and the reference implementation — a spec without a TCK is explicitly treated as incomplete, not just under-tested (`db.apache.org/jdo/tck.html`, `en.wikipedia.org/wiki/Technology_Compatibility_Kit`).
- **The suite has a distinct audience from the code it tests, and that audience behaves differently around it.** Kubernetes' conformance program exists so that a *user*, not the vendor, can trust that "Certified Kubernetes" means the same thing across clusters they didn't build — certification lets vendors put the name and a logo on products, and staying certified requires re-proving conformance against each new upstream release at least yearly (`kubernetes.io/blog/2017/10/software-conformance-certification`, `cncf.io/training/certification/software-conformance`). The suite is consumed publicly, not just privately during CI.
- **Passing a conformance suite and being *actually correct* are shown, repeatedly, to be different claims — including for funded, mature, widely-trusted systems.** Jepsen has analyzed 20+ databases, coordination services and queues since 2013 and found replica divergence, stale reads, read skew and lost writes in systems that had already shipped with confidence-inspiring marketing language; CockroachDB and TiDB were both shown to mishandle transaction retries under timestamp changes years into production use (`jepsen.io/analyses`, `cockroachlabs.com/blog/jepsen-tests-lessons`, `hoverbear.org/blog/common-safety-pitfalls-found-by-jepsen`). The finding isn't "testing catches bugs" — it's that *self-reported* conformance is not evidence, only an external, adversarially-designed suite run against the real thing is.
- **When a shared abstraction spans implementations that are allowed to have genuinely different capabilities, the suite needs a formal, visible "this backend can't, and here's why" mechanism — silent skipping is treated as a defect in the suite itself.** OpenDAL's behavior-test suite (Rust, 50+ storage backends behind one trait-like API) lets a backend declare `OPENDAL_TEST_CAPABILITY_OVERRIDES` so tests match what that backend actually supports rather than forcing every backend toward one idealized capability set, and tests are skipped only when a backend is unconfigured, not silently (`github.com/apache/opendal/.../behavior/README.md`). Ceph's `s3-tests` similarly tags tests by attribute so a runner can filter by what a given S3-compatible target is expected to support, because AWS itself doesn't uniformly enforce its own spec (`github.com/ceph/s3-tests`).
- **A conformance suite that spans real disagreement between implementations is treated as the valuable kind; one that only spans similar implementations is treated as unproven.** The `object_store` crate (Apache Arrow, originally InfluxData) spans S3, GCS, Azure, local filesystem, memory and HTTP/WebDAV behind one trait, explicitly so the same code runs unmodified across clouds and local test environments — the crate's stated value proposition *is* the breadth of backend disagreement it survives (`github.com/apache/arrow-rs-object-store`).
- **Standards bodies use "has a passing test" as the literal gate for a feature existing at all, not as a nice-to-have afterward.** Test262 (ECMAScript) requires tests for a language proposal to reach Stage 4 — a feature isn't considered part of the language until conformance tests for it exist and pass across implementations, and the suite's own change log tracks language evolution (`github.com/tc39/test262`, the Test262 Technical Rationale Report). WASI's `wasi-testsuite` is the equivalent for WASI runtimes: a single shared suite with per-runtime adapters (wasmtime, wasm-micro-runtime, etc.), so "conformant to WASI 0.3" means the same executable claim regardless of which runtime is asked (`github.com/WebAssembly/wasi-testsuite`).
- **In the Rust ecosystem specifically, "run one test body against N trait implementations" is a known pain point that individual projects solve for themselves, not an idiom the ecosystem has converged on.** A 2020s-era how-to on reusing tests across multiple trait implementations describes needing test fixtures "which Rust does not support by default" and reaches for `rstest`/`rstest_reuse` to parametrize a shared test body over different backend fixtures (`dev.to/yaghmaie/...`). Searches for a general-purpose "conformance suite for trait implementors" crate on crates.io surface no dominant, widely-adopted answer — only narrowly-scoped or unrelated `test*`/`*kit`-named crates. There is no Rust equivalent of "the TCK pattern" that a new project can reach for; each abstraction-with-many-backends project (OpenDAL, `object_store`, and now `happenstance`) has built its own.

## Implications for the idea

- **This initiative's own stance is not idiosyncratic — it's the converged shape of a known genre.** "An adapter that compiles but has not run the conformance suite is not an adapter" and "a rule no adapter can fail is decorative" (both already load-bearing constraints in the intake brief) are exactly what TCK, Kubernetes conformance, and Jepsen's whole premise say in other domains: a private claim of correctness is not evidence, only a passing run against an external, adversarially-maintained suite is. That corroborates the brief's "evidence beats argument" stance with an established precedent, not just internal conviction — worth naming as *why* the bar is what it is, not only *that* it is.
- **The moment `happenstance-testkit` is published, its audience changes in a way the desired outcomes don't yet name.** Every example above (TCK, Kubernetes conformance, test262, wasi-testsuite) shows that once a conformance suite leaves the originating team's CI and becomes something outside authors invoke, the suite's own permissiveness or strictness becomes publicly scrutinized, and "conformant" becomes a claim other people make about their own work using this project's suite as the referee. That's a sentiment/behavior question worth carrying into discovery — who, besides this project's own six skeleton crates, is expected to ever run `event_store_conformance!` against something this project didn't build, and what do they expect "green" to mean when they do?
- **The capability-declension design already chosen (per-fixture `Capability` constants, a stated reason rather than a vanished rule) matches the pattern every mature multi-backend suite converges on independently** (OpenDAL's capability overrides, Ceph's attribute-filtered tests) — evidence this is a well-trodden necessity for a suite spanning backends that "genuinely disagree," not a bespoke design risk unique to this contract.
- **Rust offers no existing idiom or dominant crate for "conformance suite as a shipped product" to be consistent with or deliberately diverge from.** Adapter authors arriving from outside this project won't bring a prior mental model of what consuming a Rust conformance-suite-crate feels like (unlike a Java author who has met a TCK before); their first experience of the *idea* of a testkit crate may be this one. That's a fact about audience readiness worth carrying into whatever stage evaluates the testkit's own documentation and discoverability — there is no existing genre convention it can lean on being recognized.
- **Every precedent that spans genuinely disagreeing backends treats that disagreement as the point, not a risk to be minimized** (`object_store` across clouds, OpenDAL across 50+ services, this project's own postgres/no-cursor/graph-shaped skeletons). That reinforces the brief's already-stated axis-of-disagreement framing for the port freeze, rather than adding a new one — it confirms the *kind* of evidence this initiative is already reaching for is the kind the wider practice treats as real proof, not a novel methodological bet.
