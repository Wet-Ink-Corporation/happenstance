# storage-agnostic-ports-that-survived-a-second-database

## Findings

- **The industry's converged answer to "backends genuinely disagree" is declared capability, not a lowest common denominator.** Apache OpenDAL — which unifies 50+ storage backends (object stores, filesystems, key-value databases) behind one API — explicitly rejects forcing every backend down to shared behavior: "OpenDAL uses Capability to describe the capabilities of different services and adopts native features of those services whenever possible." (https://opendal.apache.org/docs/vision/)
- **The same pattern was independently arrived at in an unrelated domain, at much larger stakes.** Kubernetes' Container Storage Interface conformance suite (`csi-test`) does not fail a driver for lacking an optional capability — it skips the corresponding checks and reports why, e.g. "Controller Publish, UnpublishVolume not supported," because CSI drivers self-declare which capabilities they implement and the sanity suite respects that declaration rather than treating absence as failure. (https://kubernetes.io/blog/2020/01/08/testing-of-csi-drivers/, https://github.com/kubernetes-csi/csi-test/blob/master/pkg/sanity/README.md)
- **The nearest domain peer to this project rejected storage-agnosticism outright, and its stated reason is the exact invariant this initiative's provisional port exists to protect.** Marten (a widely used .NET event store) is deliberately Postgres-only. Its creator's own rationale centers on being able to perform "event capture, document database changes, and potentially just raw SQL commands inside of the same native database transaction" — i.e., he gets the one-transaction guarantee for free by refusing portability, contrasting this against GetEventStore's "standalone, language agnostic" approach as the road not taken. Marten's docs add that porting the event-store piece to another database is "highly unlikely." (https://jeremydmiller.com/2016/04/25/marten-as-an-event-store-now-and-the-future-vision/, https://martendb.io/events/)
- **A production abstraction that has survived many real, disagreeing implementations for over a decade still has live, acknowledged seams.** Go's `database/sql` interface is the standard example of a storage-agnostic port that "worked" — dozens of drivers exist — yet its own maintainers (via the pgx driver author's writing) describe a structural limitation: `Scanner`/`Valuer` implementations "don't have access to connection information, the PostgreSQL value type, or the value format," a context gap baked into the interface from early on that newer, richer drivers still have to work around rather than fix. (https://vonng.com/en/pg/pg-go-driver/, http://go-database-sql.org/surprises.html)
- **Surviving contact with a second implementation is not a one-time proof — semantics drift silently between adapters unless something forces reconciliation.** Rails' ActiveRecord adapter layer let PostgreSQL's `#tables` return only tables while MySQL/SQLite's `#tables` silently also returned views for years; the inconsistency was only caught and scheduled for correction long after both adapters existed and passed their own tests. (https://deepwiki.com/rails/rails/2.1-database-connection-system-and-adapters)
- **Object-store abstractions that succeeded did so by shaping the port around the operations the real backends share, not around any one backend's native affordances.** `object_store` (donated to Apache Arrow, used across DataFusion/InfluxDB) is deliberately "not meant to replace the full-blown cloud SDKs" and is explicitly modeled on object-store semantics (stateless, atomic operations) rather than filesystem semantics (cursors, seek) — a design choice stated as the reason it stays portable across S3, GCS, Azure Blob and local disk. (https://docs.rs/object_store, https://crates.io/crates/object_store)
- **Where a genuinely different backend forces a real choice of dispatch strategy, there is no consensus winner — only a documented tradeoff.** Diesel supports Postgres/MySQL/SQLite via a `Backend` trait resolved at compile time (monomorphized per backend, zero runtime cost, but code must be generic over the trait or built per-feature-flag); SeaORM instead compiles business logic once and branches on backend differences at runtime. Both are shipped, maintained answers to the same "second backend" problem, and the tradeoff (compile-time specialization vs. runtime dispatch) is the whole difference. (https://colliery.io/blog/dual_backends/, https://www.sea-ql.org/SeaORM/docs/internal-design/diesel/)
- **General software-design literature converges on the same caution the intake brief already states as a constraint: an abstraction validated against too few, too-similar implementations is unearned.** The "Rule of Three" (wait for a third real use before generalizing) and Sandi Metz's "the wrong abstraction" (duplication is cheaper than a false generalization, and the fix when caught early is to unwind back to duplication rather than patch the abstraction with conditionals) are both mainstream, widely cited positions — not fringe — arguing that premature or under-tested generalization produces code "littered with conditional logic to behave different ways in different scenarios." (https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming), https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction)

## Implications for the idea

- **The closest real-world peer to this project chose the opposite path, and named the same invariant this initiative is trying to prove.** Marten gets "read-model write and checkpoint in one transaction" — the exact property `ProjectionStore`'s freeze depends on — by simply not being storage-agnostic. That is a genuine, citable counter-position a knowledgeable reader (an adapter author, a prospective user comparing this library to Marten) will bring up unprompted. This is not evidence to abandon storage-agnosticism; it is evidence that "why bother, when the leading precedent didn't" deserves a stated, honest answer somewhere the audience will find it — the kind of answer this initiative's own vision already calls for ("honest answers — not silence").
- **The capability-declaration pattern this project has already chosen for its testkit (a fixture states `SECOND_HANDLE`/`REOPEN`, a declined capability still runs and reports its stated reason) has real, independent precedent at meaningful scale** — OpenDAL's `Capability` struct and Kubernetes CSI's sanity-test skip-with-reason mechanism both converged on the same shape from unrelated domains. That convergence is evidence the *category* of design (not any specific implementation) has a track record, which is useful context for how much confidence to place in an approach already decided rather than a reason to change anything.
- **"Passed the suite against N adapters" is a snapshot, not durable proof.** Two of the cited success stories — Go's `database/sql` and Rails' ActiveRecord — show that even mature, widely-adopted storage-agnostic ports carry either a live structural leak (Go) or silently drifted per-adapter semantics that went undetected for years (Rails). This bears on how "the port survived a second database" should be understood as a claim: it is a statement about what has been checked, not an assurance nothing further will surface once a third or fourth adapter with a genuinely different shape exists — which the brief's own phase-11 "does the freeze hold" question already anticipates.
- **External literature independently supports the brief's own constraint that a rule/port needs implementations that disagree on the axis in question, not just more implementations of the same shape.** The Rule of Three and "the wrong abstraction" are mainstream engineering positions, not idiosyncratic ones, that a generalization proven against near-identical cases is unearned and costly to unwind later — which is direct external corroboration for the standing project rule that a conformance rule and a port freeze are only as credible as the *spread* of what has been run against them.
- **Where real second/third implementations force a design fork (Diesel vs. SeaORM's compile-time vs. runtime dispatch), the two shipped answers are genuinely different, not one "correct" and one "wrong."** This is offered as scene-setting rather than a suggestion: the sector this initiative sits in has no single obviously-right way to reconcile backends that disagree, only visible, documented tradeoffs each community lives with.
