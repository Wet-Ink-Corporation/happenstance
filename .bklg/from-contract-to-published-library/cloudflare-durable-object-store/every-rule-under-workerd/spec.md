## One-line PR slice

Add the crate's conformance target invoking the shipped `event_store_conformance!` with `emit = happenstance_testkit::__emit_wasm` against `CloudflareFixture`, register it as a **row** in the gate step built by `wasm-execution-seam` so one `cargo xtask ci` executes every event-store rule under a real Durable Object runtime, and state the concurrency family's non-invocation as a documented reason rather than an absence.

## Executive summary

This is where project AC-004 finally closes and where the project's proof artefact first exists. `wasm-execution-gate-step` (HS-S0048) built a seam that *executes* wasm32 conformance rules inside `cargo xtask ci`, proven against a target that already passed (`crates/happenstance-testkit/tests/memory_conformance_wasm.rs`). `durable-object-host-and-fixture` (HS-S0053) landed the Durable Object host and `CloudflareFixture`. Neither, on its own, has run a single rule against a real `!Send` store on the target the whole two-flavour port design exists for.

This PR lands the three lines that join them, and the machinery that makes those three lines *checkable*: one test target in `crates/happenstance-cloudflare/tests/` shaped verbatim like `memory_conformance_wasm.rs:19-27`; `wasm-bindgen-test` as a **target-scoped** dev-dependency of this crate, because the attribute resolves in the caller's scope and never in the testkit; a row in the executed-target registry HS-S0048 established, so no second step and no second runner wiring exists; an anti-vacuity entry that asserts the emitted rule names against `for_each_event_store_rule!` **before** anything runs; and a paragraph in the crate's own documentation stating why `event_store_concurrency_conformance!` is not invoked here.

The delta is deliberately thin in code and thick in what cannot happen afterwards. **No adapter body changes, no fixture changes, no measured limits.** The value is entirely negative-space: after this merges there is no bespoke emitter, no `#[cfg]` over any individual rule, no wasm-only rule list anywhere in the tree, and no configuration in which the Cloudflare target compiles to nothing and the gate prints green on `running 0 tests`. Project AC-002's claim is that the rule set is *structurally* single-sourced rather than promised to be; this story is what makes that sentence true of an adapter rather than of the testkit's own fixture.

## Context pack

**Decision 1 — the harness is three lines of the shipped macro, and anything longer is a signal that something is being selected.** ARCH-AC-04 fixes the shape: a test target *in this crate* invoking `happenstance_testkit::event_store_conformance!` with `emit = happenstance_testkit::__emit_wasm`, copied verbatim from `crates/happenstance-testkit/tests/memory_conformance_wasm.rs:19-27` with `MemoryFixture::new()` swapped for `CloudflareFixture::new()` (`../_decomposition.md`, Architecture ARCH-AC-04 and §4c). **No new emitter, no rule list, no `#[cfg]` over any individual rule.** The macro's general arm is `mod_name = …, emit = …, fixture = …` (`crates/happenstance-testkit/src/lib.rs:315-342`), and it expands `for_each_event_store_rule!` at `:340` — which is why "every rule, no wasm-only subset" is a structural property of this file rather than a claim about it.

**Decision 2 — the named wrong implementation is a bespoke emitter, and it defeats every existing detector.** The emitter is a parameter by design: the testkit is in no position to know which runtime an adapter is tested on, so it accepts `emit = <path>` and invokes it as `emitter!(rule_a, rule_b, …)` (`crates/happenstance-testkit/src/registry.rs:16-53`). **Nothing anywhere checks that an emitter emits one item per identifier it is handed.** A `macro_rules! __emit_wasm_cloudflare` living in this crate's `tests/`, wrapping most rules in `#[wasm_bindgen_test]` and quietly dropping the three this runtime cannot pass, passes every check in the tree: `no_orphan_rules` compares the enumeration against a scan of `suite.rs`'s own source and never looks at a harness at all (CF-24, `spec/SPECIFICATION.md:7950` and its limits paragraph — it cannot see a rule introduced by a macro expansion); `capability_skips_are_reported` runs inside the *testkit's* binary against `DecliningFixture` and never sees an adapter's harness (`crates/happenstance-testkit/tests/mutation_coverage.rs:3166-3183`). The gate would show a green run of a suite three rules short, and the rule count is printed nowhere. A softer variant needs no new macro at all: `#[cfg(not(target_arch = "wasm32"))]` over the whole target, so it compiles to nothing, the run finds zero tests, and `cargo test` exits 0.

**Decision 3 — the detector therefore lives in `xtask`, and the testkit hands the job over in writing.** `crates/happenstance-testkit/tests/mutation_coverage.rs:3176-3183` states it plainly: libtest exposes nothing programmatically, a `#[test]` cannot enumerate the binary it lives in, so CF-18's *emission* half "is only checkable from outside the process, via `cargo test -- --list`. That belongs to an `xtask` step, not to a `#[test]`." This story is the first caller that needs it. The mechanism already exists in the `xtask/src/proof.rs` shape — `Artefact { package, target, tests }` (`:58-70`) asserting named tests out of `--list` *before* running them (`:183`, `:298`), because "`cargo test` exits 0 on `running 0 tests`" and naming the target is checking the filename (`proof.rs:9-23`). `happenstance_testkit::__emit_rule_names!` (`crates/happenstance-testkit/src/registry.rs:290-295`) expands to a `[&str; N]` of the rule names for exactly this kind of cross-check, so the expectation list can be *derived* rather than hand-copied — and a hand-copied list here would reintroduce the second enumeration the whole design forbids.

**Decision 4 — this story adds a row, not a step. That is a contract, and it points backwards.** HS-S0048's AC-006 already committed to it: the executed targets are a declared list, "the way `ARTEFACTS` takes a row", and an implementation that hard-codes `-p happenstance-testkit --test memory_conformance_wasm` into `Step.args` is the wrong implementation that story rejects (`../wasm-execution-gate-step/spec.md`, Context pack Decision 7 and AC-006). So the correct diff here touches `xtask` by adding one registry row and nothing else — no second `Step`, no second `CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUNNER` wiring, no second `--target` plumbing. **If registering a row turns out to require rebuilding the seam, HS-S0048 is not done and that is the finding to report** — not something to absorb by writing a parallel step here.

**Decision 5 — "every rule" has a precise referent, and stating it is not optional.** Three rule families ship (`crates/happenstance-testkit/src/lib.rs:91-110`). AC-002's claim is scoped to the **event-store** family. `event_store_concurrency_conformance!` binds `F::Store: EventStore + Send` and its module is `#[cfg(not(target_arch = "wasm32"))]` (`crates/happenstance-testkit/src/lib.rs:101-110`, `:168-173`) — a `!Send` adapter cannot invoke it and *is not expected to*. What is **not** optional is saying so: the non-invocation is documented with its reason in this crate's own docs, and cited later from ADR-0023. Leaving it a silent absence is precisely the failure project AC-003 and BR-13 exist to prevent, and the project's risk register names it (`project.md`, Risks, *"every rule" needs a precise referent*). The **model** family is the same question with a different answer to find: it sits behind the off-by-default `proptest` feature and `fixtures::strategies`/`model` carry the same target condition for the same reason — *a feature is not target-scoped* (`crates/happenstance-testkit/src/lib.rs:176-183`) — so `proptest` is not in the graph on `wasm32` at all. Its status is stated in the same paragraph rather than left for a reader to derive.

**Decision 6 — a declined capability's reason must reach a human, and on this target the default is silence.** A rule guarding a capability the fixture declines is **still emitted as a test**; it returns `RuleOutcome::Skipped` (`crates/happenstance-testkit/src/contract.rs:477`) and the harness prints the fixture's stated reason. `__emit_wasm` routes it through `RuleOutcome::skip_line` (`contract.rs:500-503`) into `console_log!` rather than `println!` (`registry.rs:276-288`), because `println!` is a silent discard on `wasm32-unknown-unknown` — the reason `skip_line` is public at all (`registry.rs:55-60`). The gate's `tests` step carries `--show-output` for the same reason on the host (`xtask/src/main.rs:132-151`); HS-S0048 ported the equivalent to the execution step. This story's obligation is to *observe* that it worked against a fixture that actually declines something, and to paste the lines into the report — a stated reason that reaches a void is AC-003 satisfied by silence.

**Decision 7 — the dev-dependency is target-scoped, and that is not a stylistic preference.** `wasm-bindgen-test` must be in **this crate's** `[target.'cfg(target_arch = "wasm32")'.dev-dependencies]`, mirroring `crates/happenstance-testkit/Cargo.toml`'s own block, because `#[::wasm_bindgen_test::wasm_bindgen_test]` resolves in the *caller's* scope and never in the testkit (`../_decomposition.md`, Architecture §4c). A feature would be wrong for the reason the testkit already documents in a comment: a feature is not target-scoped, so `--all-features` would set it on the host too (`crates/happenstance-testkit/src/lib.rs:176-183`). Nothing lands in `[dependencies]`; `happenstance-cloudflare` is a crate this initiative intends to publish (`../publish-ready-crate/`), and a dev-dependency does not travel to a consumer.

**Decision 8 — the persona slice, and which two of the three observe this.** The story map names three observers (`../_storymap.md`, Backbone). The **gate reader** gets activities **C** and **D**: *prove the edge store conforms — every rule, executed*, and *know what this runtime cannot do, and why* — both in the terminal scroll of the run they already started, not in a second tool on a machine they do not have. The **adapter author** gets a loop that terminates on this runtime too: one entry point, a pass or a named failure per rule, no storage shape quietly assumed (`project.md`, DR-6). The library consumer observes nothing here, and this story ships **no public API** — the target lives in `tests/`, and the only `src/` edit is documentation.

**Decision 9 — what a first green run does and does not discharge.** The dependency edges make this easy to get backwards: `measured-store-limits` (HS-S0055) depends on *this* story, so the first green run happens with `CloudflareFixture`'s three `Option<usize>` ceilings at whatever HS-S0053 left them. **That run is not the discharge of CF-40**, and this story must not be reported as though it were. Equally, if a rule fails only on `wasm32`, the response is a finding naming the rule and the divergence — never a `#[cfg]` and never a subset, which would fail project AC-002 by construction (`../_decomposition.md`, Architecture Notes §7.4).

**Decision 10 — nothing `[FROZEN]` is amended, and CF-23 is asking for exactly this.** CF-23 requires three harnesses demonstrated in-tree — tokio, blocking, and `wasm-bindgen-test` — and forbids the testkit emitting a runtime attribute from its own expansion (`spec/SPECIFICATION.md:7920-7951`). This story satisfies both by *using* the shipped `__emit_wasm` parameter, and is the third harness applied to a real adapter rather than to the testkit's own fixture. If this runtime turned out to be unable to host the family CF-23 assumes, the response is a new decision atom and a re-plan, written first — never a clause edit and never a quietly narrowed harness (`../_storymap.md`, discover gate box 7).

**What this story does not decide.** The fixture's capability constants and its measured ceilings (HS-S0053 declares them, HS-S0055 measures them); the runner's mandatory-versus-probe shape and the fate of `.github/workflows/ci.yml`'s standalone `wasm-conformance` job (HS-S0048 settled both); ADR-0023's authorship and CF-40's ownership (`adr-0023-and-atom-resolutions`, HS-S0058, minted through `/redkiln:kb-ingest`, never hand-written); the WF-11 falsifier and the ES-32 verdict (HS-S0056, HS-S0057). This story produces the executed run and the recorded observations those stories consume.

## Risks and coupling (PR-scoped)

- **This PR is the first time anything in the workspace runs a rule on the target the `!Send` design exists for.** Expect failures that are real defects in `durable-object-write-path`/`durable-object-read-path` rather than in this diff. The coupling is deliberate — that is what an instrument is for — but the *reporting* discipline is this story's: name the rule, name the owner, do not fix it inside this boundary and do not `#[cfg]` it away (EC-002, EC-004).
- **Two upstream contracts are being cashed at once.** HS-S0048's "add a row, not a step" and HS-S0053's `CloudflareFixture::new()`. If either has drifted, this story discovers it, and the correct response is a finding against the drifted story (EC-003), not a local workaround. That is also why this story cannot start earlier: both edges are load-bearing, and a runner with nothing to run or a fixture with nowhere to run it is half a proof.
- **The anti-vacuity row is the whole story's load-bearing member, and it is the easiest thing to soften under time pressure.** Every softening — hand-copying the expectation, dropping the `--list` assertion, listing only a few rules — leaves a green gate and an unfalsifiable claim. EC-005 names the only permitted fallback.
- **`cargo xtask ci --fast` becomes more expensive for every subsequent story in this project** once a second executed wasm32 target is in the row list. That cost was accepted at the deployment brief; this story is where it becomes real, so NF-002 asks for the measurement rather than an impression.
- **Report-scope creep toward CF-40.** A green run at HS-S0053's declared ceilings looks like a discharge of the fixture-limits question and is not. The report must say so explicitly (AC-008); `measured-store-limits` depends on this story precisely because the numbers come after the run, not before it.
- **`.kb/` pressure.** This run produces exactly the material an ADR wants, and the temptation is to write it. Every KB write in this project belongs to `adr-0023-and-atom-resolutions` through `/redkiln:kb-ingest`; hand-authoring an atom here reproduces the failure reverted at `0269720` (`CLAUDE.md`, **Where the work lives**).
- **Blast radius.** Files touched: this crate's `tests/`, its `Cargo.toml`, its `lib.rs` docs, `xtask/src/proof.rs`, `xtask/src/main.rs` (only if the row list lives there), `CHANGELOG.md`, and this story's folder. No other crate, no adapter body, no clause, no `.kb/` atom.

## Clarifications resolved during spec

1. **The AC set is exactly the eight the front half enumerated** — AC-001 … AC-008. None added, none dropped; the ledger matches one-for-one.
2. **The target's filename and `mod_name` are fixed here rather than left to the implementer**: `crates/happenstance-cloudflare/tests/durable_object_conformance.rs` with `mod_name = dcb_conformance_wasm`. Not a style preference — the `xtask` row's expected names are `<mod_name>::<rule>`, and a name chosen at implementation time is a name the ledger and the registry row cannot both be written against in advance.
3. **The `xtask` expectation list is derived, not hand-copied**, and that is a deliberate divergence from `ARTEFACTS`' existing rows. `proof.rs:25-45` argues that duplication is the mechanism *for clause citations* — a rename should have to be noticed. Here the thing being guarded is different: a **harness against the enumeration**, where a hand-copied list is itself the second enumeration project AC-002 forbids. Both arguments are correct about different rows; this spec says which applies to this one.
4. **The model family's status is stated, not run.** `proptest` is off by default and `fixtures::strategies`/`model` are target-gated for the same reason the concurrency family is (`crates/happenstance-testkit/src/lib.rs:176-183`), so it is not in the graph on `wasm32` at all. The discover stage deferred this to spec; the resolution is that AC-006's paragraph states it and no invocation is attempted.
5. **AC-005 has an answer for the case where the fixture declines nothing.** A green run with zero `SKIP` lines proves the reporting path exactly as well as an empty log proves a logger works. The criterion therefore requires either an observed decline or a recorded-and-reverted scratch decline, so the path is demonstrated either way.
6. **The runner-absence behaviour is inherited, not re-decided.** EC-001 defers wholly to HS-S0048's AC-004. Two stories independently deciding what happens when a tool is missing is how a gate acquires two answers.
7. **`proof.rs`'s "three targets today" sentence is in scope.** The PR boundary lists `xtask/src/proof.rs`; correcting a doc comment this row makes false is part of adding the row, not scope creep.
8. **Nothing here renders a surface, and the composition family of §6.7/D6 is therefore empty by a signed-off decision** rather than by omission — `../_design.md` records N/A for the entire project. The state family still binds, in the gate's own output, and every applicable invariant is an AC row rather than a prose bullet.
