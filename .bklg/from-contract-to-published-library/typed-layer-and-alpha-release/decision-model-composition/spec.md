## One-line PR slice

Land the internal declarative macro that implements the sealed `Boundary` trait for
tuples of decision models — `(B1, B2)`, `(B1, B2, B3)`, … through arity 8 — so a
caller composes consistency boundaries by writing a tuple, the composed `Query` is
the union of the members' own query fragments, and each member absorbs only the
events its own query nominated.

## Executive summary

**Delta over the slice-mate.** `domain-event-and-decision-model` lands the vocabulary
— `DomainEvent`, `DecisionModel`, and the sealed `Boundary` trait that carries the
*derived* query, blanket-implemented for every `DecisionModel`. At that point a
caller can express exactly **one** consistency boundary. This PR makes N of them one
boundary: seven `impl Boundary for (…)` blocks, emitted by one internal
`macro_rules!`, each OR-ing its members' query fragments into a single `Query` and
routing each read event to the members that nominated it.

**Why it is a story and not a line.** Composing several decision models into one
query *is* the dynamic-consistency-boundary mechanism — it is what the crate root
already promises a reader in prose (`crates/happenstance/src/lib.rs:44-46`: *"Composing
several into one query is the mechanism that makes a dynamic consistency boundary
dynamic"*) and what the worked example hand-rolls today as a two-item
`Query::from_items` (`examples/course-subscriptions/src/main.rs:114-125`). Until the
tuple impls exist, that sentence is a roadmap bullet, and the example's DCB case has
no typed form to be rewritten onto in M6.

**What this PR does not do.** It adds no new *name* to the crate root. The design
files tuple composition under *revealed* — *"it is a capability of a type already on
the page, not a name of its own"* (`../_design.md:825`) — so the entire public delta
is seven impl blocks plus one line in the crate-root vocabulary region. The macro
itself stays private; a caller who has to write a macro invocation where a tuple
would do has been charged ceremony DT-2 is being measured on (`../_design.md:639`).

## Context pack

Everything below is a **decision already taken**, not an option. Read it before
writing code; open an anchor only when its row says to.

### 1. Composition is a tuple, and the macro is invisible

`impl Boundary for (B1, B2)` … `(B1, …, B8)`, generated by one internal
`macro_rules!`. **Rejected and closed**: an exported `compose!` macro — *"the caller
writes a macro invocation where a tuple would do, and a macro in the caller's face is
ceremony DT-2 is being measured on"* (`../_design.md:639`). The arity ceiling is
**8**, chosen for the rendered page: rustdoc emits one impl block per arity, and
sixteen of them buries `Boundary`'s item page. The ceiling is the implementer's only
free variable that has already been spent (`../_decomposition.md:715-726` lists *"the
composition macro's arity ceiling"* as deliberately not prescribed by the brief;
`_design.md` then prescribed it, and `_design.md` is signed off — `../_design.md:1224-1235`).

### 2. The composed query is a union, never a narrowing

Query items combine with **OR** — *"an event matches the query when it matches any
item"* (`crates/happenstance-core/src/query.rs:131`). So the composite's items are
its members' items, concatenated in member order and otherwise untouched: no dedup
that could drop a member's constraint, no merge that could turn two items into one
narrower item. A composed boundary that selects **fewer** events than the union is a
lost update with no diagnostic — the same failure the `Query` enum's own seal exists
to prevent — and it is the wrong implementation this story's unit test must reject.

### 3. `query()` stays fallible, and a member's error is the composite's error

`Boundary::query` returns `Result<Query, InvalidQuery>` (`../_design.md:423-435`).
The composite calls each member's `query()` and propagates the **first** `Err`
unchanged; it never substitutes `Query::all()`, and it never drops a failing member
and carries on with the rest. `InvalidQuery::UnconstrainedItem` means *"this boundary
constrains nothing, which is `Query::all()` and must be said out loud"*
(`crates/happenstance-core/src/error.rs:99-102`), so swallowing it would silently
widen a caller's boundary to the whole log — the inverse of §2's failure and just as
undiagnosable. This is the residual `_design.md` records as **defect candidate D-1**
(`../_design.md:652-672`): the `Result` is unreachable for well-formed models and is
kept anyway, because `happenstance-core` is frozen and we do not `unwrap`.

### 4. Members share one `Event` type — by where-clause, on purpose

The tuple impls constrain every member to the same associated event type
(`B2: Boundary<Event = B1::Event>`, and so on up the arity). This is forced, not
preferred: the command loop's `decide` closure returns `Vec<B::Event>` for the
*composed* `B` (`../_design.md:514-524`), and the DSL hands back `Decision<B::Event>`
(`../_design.md:585-586`). A synthesised sum type over the members' event types is
not a thing a `macro_rules!` can produce without minting a public name — which would
be a name of its own, which §1 forbids. One domain enum per composed boundary is also
what the worked example is: `subscribe` spans capacity, seats and one student's own
history over a single event vocabulary (`examples/course-subscriptions/src/main.rs:114-125`).

### 5. `absorb` routes by nomination, not by arrival

Each member absorbs only the events **its own** query matches; a member never folds an
event outside its boundary just because a sibling nominated it. `Query::matches` is
the predicate (it takes the event type and tags and is the reference filter every
adapter is measured against — `crates/happenstance-core/src/query.rs`). The design
already fixes the two ends of this: an event the member did not nominate is skipped
**silently, by nomination**, while an event that *was* nominated and cannot be decoded
returns `CodecError::UnknownEventType`, *"because that is a real disagreement between
`EVENT_TYPES` and the fold"* (`../_design.md:937-940`). Routing by arrival instead —
handing every read event to every member — is the second wrong implementation this
story's tests must reject: it compiles, it passes any test that composes two models
over disjoint tags, and it corrupts the fold the moment two models share an event type.

### 6. The seal extends to the tuples, or it is not a seal

`Boundary: sealed::Sealed`, and `Boundary` is sealed *"because the tuple impls and the
blanket impl must stay the only ones; a third implementor could hand-maintain a
query"* (`../_design.md:735`). So the same macro emits **two** impls per arity —
`Sealed` and `Boundary`. `sealed::Sealed` is explicitly on the list of items that were
considered for `pub` and are not, alongside this very macro (`../_design.md:753-757`).

### 7. Macro discipline, because the diagnostic is the deliverable

Two rules from the constitution bind here and both have a named failure this
repository has already met. **RS-41-1** — every path the expansion emits is
`$crate::`-qualified; `macro_rules!` hygiene covers locals and labels, *not* item
paths, which resolve where the expansion lands
(`standards/rust/41-declarative-macros.md:12`). It still binds for a private macro:
the expansion lands in whichever module the impls live in, and `$crate` is the only
spelling invariant under a module move. **RS-41-3** — arms are ordered
most-literal-first, because *"the matcher tries arms top to bottom and takes the first
that consumes the whole invocation"* and `$x:expr`/`$t:ty` fragments swallow more than
they look like they do (`standards/rust/41-declarative-macros.md:95`). The ux brief
binds both to **AC-U07**: *"a guarantee whose diagnostic names a file the user did not
write is a guarantee they cannot act on"* (`../_decomposition.md:132-139`).

### 8. The mount is the crate root, and the glob survives

Every new item is `pub use`d at `crates/happenstance/src/lib.rs` **beside** the
surviving `pub use happenstance_core::*;` (`:75`), and nothing may shadow a contract
name (**AC-A01**, `../_decomposition.md:355-362`). Here the impls carry no new name,
so the mount is the *doc* half of the same root: the `DecisionModel` bullet in the
module doc's vocabulary region (`crates/happenstance/src/lib.rs:44-46`) stops
promising *"Composing several into one query…"* and starts linking — one line,
revealed, with an intra-doc link to `Boundary` (`../_design.md:772`, `:825`). A
capability reachable from nothing is the failure the *Composition roots* section
exists to prevent (`../_decomposition.md:452-459`).

### 9. The persona slice this realises

Beat 1 of *"Choose a contract before a database"* — **model a consistency boundary**
(`../_storymap.md:24`). The reader is P4-shaped: one bounded sitting, new to idiomatic
Rust, and every construct that costs them a page is a first-hour cost
(`CLAUDE.md`, *Who you are working with*). That is why the answer to *"how do I check
two boundaries at once?"* must be *"put them in a tuple"* and must fit in the one line
§8 buys.

### 10. Two constraints inherited, not re-decided

**No port is touched.** `Boundary` names no store type, so nothing in this story can
introduce a `Send` bound; the two-flavour obligation is discharged by saying so rather
than by a decorative test (`../_decomposition.md:430`). **No `happenstance-core` edit.**
A convenience found mid-implementation — an infallible `QueryItem` constructor, say —
is inadmissible: it is AC-A02's route or nothing, and D-1 (§3) is already written down
for AC-012's log (`../_decomposition.md:363-371`).

## Data and migrations

**N/A — this story adds no persisted data and no schema.**

Three things that look like data and are not:

- **The composed `Query` is a value, not a record.** It is built per call from the
  members' own `query()` results and handed to `EventStore::read` /
  `AppendCondition`; nothing stores it, and no store adapter sees a composed boundary
  as anything other than a `Query` it already understands
  (`crates/happenstance-core/src/query.rs`).
- **No event, payload or tag shape changes.** Payloads stay opaque `Bytes` at the
  port; the codec tag's home is ADR-0021's and is untouched here
  (`../_design.md:674-679`).
- **No manifest or feature change**, so nothing alters what `default-features = false`
  means for a consumer (AC-A04 is M3's mount, `../_decomposition.md:381-390`).

There is consequently no migration, no backfill and no rollback step: reverting this
PR removes seven impl blocks and one documentation line.

## Acceptance criteria

Each row is a persona goal crossing the whole stack — the caller's source, the
compiler, the composed `Query` that reaches `EventStore::read`, and the rendered
page a reader lands on. **P1** is the application author (*"model a consistency
boundary once, against a contract"* — `../_decomposition.md:47`); **P4** is the
evaluator with one bounded sitting (`:48`). The journey is *"Choose a contract
before a database"*, Beat 1 — **model a consistency boundary**
(`../../initiative.md:243-244`; `../_storymap.md:24`).

Behavioural tests live in `crates/happenstance/tests/composition.rs` **on purpose**:
an external integration test proves the tuple impls are usable by a *downstream*
caller through the crate root, which is exactly what a sealed trait's impls have to
be and what a `#[cfg(test)]` module inside the crate cannot show.

## Implementation notes (non-prescriptive)

Shape, not instructions. Every one of these is a place the type checker or rustdoc
will have an opinion, and knowing it in advance is cheaper than meeting it.

- **`macro_rules!` is textually ordered.** A `macro_rules!` is in scope only *after*
  its definition in source order unless the module carrying it is annotated
  `#[macro_use]`. If the macro and the impls live in different modules, the macro's
  module has to be declared first in `lib.rs`, or the macro has to be pulled out with
  a `pub(crate) use` and imported by path (the 2018-style path import works and is
  the tidier of the two). This is the most common way an otherwise correct internal
  macro fails to compile.
- **`$crate::` still matters for a private macro.** Hygiene covers locals and labels,
  not item paths, and the expansion resolves wherever it lands. Writing
  `$crate::Boundary` rather than `Boundary` is what survives someone moving the impls
  into a submodule six months from now (RS-41-1,
  `standards/rust/41-declarative-macros.md:12`).
- **Generating arities.** Two shapes both work: a recursive arm that peels one type
  parameter at a time, or seven explicit invocations of a single non-recursive arm
  (`impl_boundary_for_tuple!(B1, B2);` … `impl_boundary_for_tuple!(B1, …, B8);`). The
  second is longer and reads better in a diff, and it makes the arm-ordering rule
  trivial because there is only one arm. Either way, order arms most-literal-first
  (RS-41-3, `:95`) — a `$($t:ident),+` arm above a two-ident arm makes the specific
  one dead on arrival.
- **The where-clause chain.** `B1: Boundary, B2: Boundary<Event = B1::Event>, …` —
  every member is pinned to the *first* member's event type rather than pairwise, so
  the error a caller sees names `B1::Event` once instead of a chain.
- **Tuple field access inside a macro.** `self.0`, `self.1`, … cannot be generated
  from a type-parameter repetition; the usual answers are to accept the indices as a
  second repetition (`impl_boundary_for_tuple!(B1 0, B2 1);`) or to destructure with
  `let (a, b) = self;` in the method body and repeat over identifiers instead. The
  destructuring form keeps the matcher simpler and is worth trying first.
- **Building the union.** Concatenate the members' `QueryItem`s in member order and
  hand them to the same constructor a single model uses
  (`crates/happenstance-core/src/query.rs`). Do not reach for a `HashSet` "to be
  tidy" — that is AC-002's named wrong implementation, and `QueryItem` need not even
  be `Hash`.
- **`absorb` and `Query::matches`.** Each member re-derives its own query to decide
  nomination. If that reads as wasteful, note NF-002: the alternative is caching, and
  caching is what makes the composite's answer depend on when it was built.
- **Doc comments on impl blocks render.** A `///` on `impl Boundary for (B1, B2)`
  appears in `Boundary`'s *Trait Implementations* section and its fences **are**
  collected as doctests. That is where the composing example belongs — the crate-root
  page keeps exactly one fence (`../_design.md:877-884`).
- **Name the alternative once, where the reader is** (RS-70-5,
  `standards/rust/70-rustdoc-obligations.md:243`): the doc comment on the arity-2
  impl is where *"an exported `compose!` macro lost because a macro in the caller's
  face is the ceremony this design is measured on"* goes. Once — not on all seven.
- **The example's multi-model case is the shape to aim at.** `subscribe`
  (`examples/course-subscriptions/src/main.rs:113-176`) spans capacity, seats and one
  student's history over a single event vocabulary; if the tuple cannot express it,
  the where-clause is wrong, not the example. Do not rewrite the example here — that
  is M6's — but do read it before choosing the signature.

## Clarifications resolved during spec

1. **Eight acceptance criteria, not six.** The front half planned AC-001…AC-006.
   Writing the interaction-quality section made two gaps unavoidable: the composition
   family (placement, transience, density, hierarchy, the four applicable
   anti-patterns) and the state family (purity, inspectability, pristine re-fold,
   feature-off link resolution) each needed a row of its own, because `redkiln verify`
   extracts ACs from table rows and a prose bullet is never gated. Bundling them onto
   AC-006 would have produced one row no single test could discharge. **AC-007**
   (composition/presentation budget) and **AC-008** (state invariants) were added;
   AC-001…AC-006 are unchanged in intent from the front half's plan. The ledger
   carries all eight.
2. **The composing example lives on the arity-2 impl block, not on the crate root.**
   The front half says this PR ships *"a doctest that composes two models"* without
   siting it. `../_design.md:770` gives the crate-root page exactly one fence — the
   first program, *"alone above the fold"* — and `:877-884` makes that fence's
   solitude the page's primary hierarchy signal. A second fence on the landing page
   would fail anti-pattern 2 outright. The example therefore lives where the
   transience policy already put tuple composition: *revealed*, one click away, on
   `Boundary`'s item page (`:825`).
3. **Behavioural tests are an external integration test, not a `#[cfg(test)]`
   module.** `crates/happenstance/tests/composition.rs` compiles as a downstream
   crate, so it proves what an in-crate test cannot: that a sealed trait's tuple impls
   are usable by someone who is not us, through the public root. The PR boundary
   already admits `crates/happenstance/tests/**`.
4. **The 9-tuple refusal is stated, not tested.** `trybuild` is absent from the tree
   and its adoption is HS-P0010's decision (`../_decomposition.md:828-841`); a
   `compile_fail` doctest is not an equivalent instrument, because rustdoc collects
   doctests from the lib target only and silently ignores an unmatched error-code
   annotation. Faking the check would be worse than naming the gap. The real
   compile-fail instrument is `compile-fail-proof-artefact`'s (M6).
5. **`happenstance`'s feature-off documentation is not gated, and this story does not
   fix it.** `xtask/src/main.rs:502-513` builds `--no-default-features` docs for
   `happenstance-core` only. Fixing it means editing `xtask/`, which is outside this
   PR boundary; AC-008 makes it a cited manual check and *Risks* routes the permanent
   fix to `edge-flavour-and-wasm-claim` and, if it bites, to AC-012's defect log.
6. **No ADR path is cited for ADR-0020.** `.kb/decisions/` holds sixteen atoms plus
   ADR-0029 at HEAD; 0020 and 0021 do not exist yet and are M1's to stage and ingest
   (`../_storymap.md:49-50`). Citing a `.kb/decisions/0020-*.md` path would be a dead
   anchor, so this spec's normative authority for the derived-query shape is
   `../_design.md` — signed off (`:1224-1235`) — together with the slice-mate's spec.
7. **EC-002 states the no-rollback fact rather than designing around it.** A composite
   whose third member fails to decode leaves the first two folded. Making absorption
   transactional would mean cloning every member on every event; the design's answer
   is already the command loop's retry from a pristine clone (AC-U13). The obligation
   this story takes on is to *write that down in the impl's doc comment*, not to hide
   it.
