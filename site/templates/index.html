Event sourcing for Rust

The boundary is not declared in advance.

A storage-agnostic, DCB-compliant event store. Each decision reads the events it depends on, and its write is refused if anything matching that read has landed since — so the consistency boundary is whatever the decision actually read.

One rule, three answers

A decision that spans two things

01The rule

A course holds thirty seats. A student takes at most five courses. Subscribing one student to one course has to respect both limits — and the two limits are about different things.

02The answer you know

Classical event sourcing asks you to choose the boundary when the schema is written: a Course aggregate or a Student aggregate. Choose either, and the other limit needs a read model and a saga. The boundary was fixed before anyone knew which decisions it would have to hold.

03The answer here

A dynamic consistency boundary is drawn per decision. The handler reads exactly the events this decision rests on — the seats taken on this course, the courses this student holds — and appends on condition that nothing matching that read has appeared since. The boundary is deliberate, but not pre-declared.

About the name

In everyday use the word means chance, and that is not the sense meant here. The sense meant is the one in as it happened: a DCB boundary is not fixed when the schema is written — it is whatever the handler's query matched. The handler designs that query on purpose; what it does not do is inherit a boundary someone drew earlier.
