Event sourcing for Rust

Keep your rules true when requests collide.

happenstance records what your application does as a log of events. When a request makes a decision, such as taking the last seat on a course, it reads just the events that decision depends on. If a new event matching what it read has been added by the time it writes, the write is refused and the decision is made again, so two requests can never both take the last seat. The same code runs on SQLite, PostgreSQL, Neon and Cloudflare Durable Objects.

What you get

Rules that hold, on the storage you already run

Rules that span several things just hold

A seat limit on a course and a course limit on a student are checked by one read and guarded by one write. No locks, no background clean-up, no overbooking.

One rule, three answers

A decision that spans two things

01The rule

A course holds thirty seats. A student takes at most five courses. Subscribing one student to one course has to respect both limits — and the two limits are about different things.

02The answer you know

Most event-sourced systems split events into fixed groups chosen up front, such as one per course or one per student, and only keep a rule consistent inside one group. A rule about a course and a student fits neither, so it ends up enforced by extra machinery: a separate copy of the data to check against, and a background process to undo the mistakes that slip through.

03The answer here

With a dynamic consistency boundary (DCB) there are no fixed groups. Each decision reads the events it needs, here the seats taken on this course and the courses this student holds, and its write is accepted only if no new event matching that read has been added since. Both limits hold, with one read and one write.

Measured, not claimed

Fast where it matters

~34 µs to check a two-thing rule

The SQLite store checks a condition spanning a course and a student in about 34 µs, and the cost stays flat as the log grows from a thousand events to a million.

~57,000 events a second

Appended to SQLite in batches of 128, about 6,900 a second one at a time. The in-memory store reaches about 4.8 million.

~189,000 events a second, rebuilt

A read model catches up from an empty start over SQLite at that rate, so rebuilding a view over a large log is minutes, not hours.

64 writers, one winner, no errors

Sixty-four requests race for the same decision. Exactly one is accepted, the other sixty-three are told to decide again, and nothing fails.

One run on one Linux machine, in September 2026; read them as orders of magnitude. The full results carry the method, the raw output and what the numbers do not show.

About the name

In everyday use the word means chance, and that is not the sense meant here. The sense meant is the one in as it happened: a DCB boundary is not fixed when the schema is written — it is whatever the handler's query matched. The handler designs that query on purpose; what it does not do is inherit a boundary someone drew earlier.
