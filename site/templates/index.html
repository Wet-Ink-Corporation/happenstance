Event sourcing for distributed Rust apps

Your data stays true, everywhere it lives.

happenstance is the data layer for Rust apps that run on devices, at the edge and in the cloud. Every change is kept, every business rule is checked, and every answer can be explained, whether the data sits in SQLite on a laptop that is offline, in a Cloudflare Durable Object near your users, or in Postgres and Neon.

Nothing lost. Nothing wrong. Nothing unexplained.

What you get

Data you can trust, on every device and every database

True offline

Every device keeps its own log and keeps working without a network. When it reconnects, every change syncs, and nothing is lost or overwritten, because a change is a fact rather than a row to fight over.

True to your rules

Seat limits, balances, quotas and unique names are checked at the moment of the write, across every record the rule touches, with no locks and no sagas. When two places act at once, you are told, with an event, never left with a silent mistake.

True to its history

The log is the source of truth. See why any record looks the way it does, rebuild a view that went wrong, add a new one over years of data, and change your event format without a migration.

True wherever it lives

SQLite on the device, Durable Objects at the edge, Postgres or Neon in the middle. The same Rust code runs on each, every store passes the same published test suite, and there is no sync service in the middle.

How your rules stay true

A decision that spans two things

01The rule

A course holds thirty seats. A student takes at most five courses. Subscribing one student to one course has to respect both limits — and the two limits are about different things.

02The answer you know

Most event-sourced systems split events into fixed groups chosen up front, such as one per course or one per student, and only keep a rule consistent inside one group. A rule about a course and a student fits neither, so it ends up enforced by extra machinery: a separate copy of the data to check against, and a background process to undo the mistakes that slip through.

03The answer here

With a dynamic consistency boundary (DCB) there are no fixed groups. Each decision reads the events it needs, here the seats taken on this course and the courses this student holds, and its write is accepted only if no new event matching that read has been added since. Both limits hold, with one read and one write.

Measured, not claimed

Fast where it matters

~34 µs to check a two-thing rule

The SQLite store checks a condition spanning a course and a student in about 34 µs, and the cost stays flat as the log grows from a thousand events to a million.

~57,000 events a second

Appended to SQLite in batches of 128, about 6,900 a second one at a time. The in-memory store reaches about 4.8 million.

~189,000 events a second, rebuilt

A read model catches up from an empty start over SQLite at that rate, so rebuilding a view over a large log is minutes, not hours.

64 writers, one winner, no errors

Sixty-four requests race for the same decision. Exactly one is accepted, the other sixty-three are told to decide again, and nothing fails.

One run on one Linux machine, in September 2026; read them as orders of magnitude. The full results carry the method, the raw output and what the numbers do not show.

How it compares

Both halves, in one library

Sync engines

Fast and offline, but conflicts are merged away or the last write wins, and most keep no history. Your business rules live in backend code you write yourself.

Event-sourcing frameworks

History, audit and rebuildable views, but on one server, usually behind aggregates and sagas, and sometimes a vendor's server too.

happenstance

Offline devices, edge and central databases syncing one history, with every rule checked where its history is complete and every view rebuildable. A library over your own databases.

Looking for collaborative text editing, or a reactive local database for a JavaScript web app? A CRDT library or a JavaScript sync engine will suit you better.

About the name

In everyday use the word means chance, and that is not the sense meant here. The sense meant is the one in as it happened: a DCB boundary is not fixed when the schema is written — it is whatever the handler's query matched. The handler designs that query on purpose; what it does not do is inherit a boundary someone drew earlier.
